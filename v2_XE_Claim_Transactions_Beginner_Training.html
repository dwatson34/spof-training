What is a Claim Transaction?

Click each stage to understand what happens when a user opens a claim for editing.

In Xuber, a transaction is a controlled unit of work on a claim. Unlike simply reading data, a transaction locks the claim, creates a working copy, tracks all changes, and commits or discards them as a single operation. Every write operation in the claims screens is a transaction.

Lock — the claim is reserved for this user

When a user starts a transaction, Xuber locks the claim record to prevent concurrent edits. No other user can start an amend, close or delete transaction on the same claim while this lock is held. The display transaction (xuTransactionMode.display) is an exception — it is read-only and does not lock.

When startNewTransaction() calls the API and the backend creates the transaction, it returns a transactionId. This ID identifies the working copy of the claim data for this specific editing session. Every subsequent API call in that session passes this ID so the backend knows which working copy to read and update.
Xuber detects the tab close via onTabCloseClicked(). This calls cancelTransaction() which tells the backend to discard the working copy and release the lock. If the tab is force-closed without this handler firing, the lock may need to be manually released by an administrator.
saveButtonHandler() calls completeTransaction(). This commits the working copy to the real claim record, releases the lock, and shows the completion dialog. The completeAndResume flag controls whether the page stays open after completion (true) or closes (false).

Transaction vs Display

Key distinction: xuTransactionMode.display is technically a transaction but it is read-only. It creates a lightweight session to track what the user is viewing (for task completion purposes) but does not lock the claim. All other modes create a proper write lock.

How a Transaction Starts

Click ▶ to step through what happens from user click to transaction ID.

Every claim transaction follows the same 5-step startup sequence. Understanding this sequence tells you exactly where to look when a transaction fails to open.

Click ▶ to step through

Click to step through
1

User clicks a transaction action

The user clicks “Amend”, “Close”, “Delete” etc. in the Xuber HTMLUI. Angular routes to the appropriate transaction component URL.

2

ngOnInit fires

The component’s ngOnInit() runs first. It sets this.claimStage = ClaimStage.Claim, calls this.IntitateDefaultSection() (base class setup), and sets this.transactionMode to the correct mode for this component.

3

startNewTransaction() is called

The base class framework calls startNewTransaction() — the abstract method each component implements. Inside, the component calls the appropriate service method: e.g. xuClaimsTransactionService.startAmendClaimTransaction(claimStage, claimReference).

4

API returns transactionId

The backend creates the transaction, locks the claim record, creates the working copy, and returns data.transactionId. The component resolves the XuDeferred with this ID: transactionIdDefer.resolve(data.transactionId).

5

Screen loads with the transactionId

The transactionId is now available to all parts of the component. Every subsequent API call in this session passes it so the backend knows which working copy to read and write. The user sees the claim data ready for editing.

Where to look when a transaction fails to open: A failure at step 3/4 appears as a red entry in the Network tab. The endpoint will be something like /XuberHTMLApi/api/claims/StartAmendClaimsTransaction. Check the Response tab for the error message — usually a business rule (claim already locked, insufficient authority) or a null claimReference.

The Shared Template

Click each tab to understand how 7 different transaction components all use the same HTML file.

One of the most important architectural decisions in the Xuber HTMLUI claims framework is that every transaction component uses exactly the same HTML template. This is not a coincidence — it is a deliberate design that makes the framework maintainable at scale.

Every transaction component — real sourceTypeScript
@Component({
  selector:
    'xu-amend-claim-transaction',

  // SAME template for all 7:
  templateUrl:
    '../../../../common/transactions/
    components/
    xuTransaction.component.html',

  styleUrls: [
    '../../../../common/transactions/
    components/
    xuTransaction.component.less',
    './xuAmendClaimTransaction
    .Component.less'
  ],
  encapsulation:
    ViewEncapsulation.None,
  standalone: false
})

What this means

All 7 transaction components point to the same xuTransaction.component.html in the common/transactions/ folder. The template renders the same structural layout every time. What changes is the data and behaviour driven by the component class — the transaction mode, the title, the menu items, the save logic.

When a bug affects the layout of ALL transaction screens, look in common/transactions/components/xuTransaction.component.html. When a bug affects only ONE transaction type, look in that component’s class file.
ViewEncapsulation.None — why it mattersTypeScript
// On every transaction component:
encapsulation:
  ViewEncapsulation.None

// Default Angular behaviour:
// CSS is scoped to this component.
// ViewEncapsulation.None:
// CSS is global — affects the
// whole page.
//
// Required here because the shared
// template renders child components
// that need the parent styles to
// apply to them.

Why None instead of the default?

Angular’s default encapsulation adds a unique attribute to CSS selectors so styles only apply within their component. Because the shared transaction template renders dynamic child components, the parent’s styles need to reach those children. ViewEncapsulation.None removes the scoping so CSS applies globally. This is why claim transaction CSS changes can have unexpected side effects — the styles are not scoped.

The template reads properties, not modes directly

The shared template does not contain @if (mode === 'amend') style logic. Instead it reads computed properties like getHeaderTitle(), isCreateTransaction and screenMenuItems that each component populates differently. The base class builds most of these; each child component overrides only what it needs to change.

The 7 abstract methods — every component must implementTypeScript
// From xuClaimsTransactionComponentBase:

  string

  boolean

  string

  string

  Promise<any>

  completeAndResume: boolean,

Why abstract methods?

The base class declares these as abstract — it compiles TypeScript to enforce that every child class implements all 7. If you create a new transaction component and miss one, the TypeScript compiler will refuse to build. This is the contract that makes the shared template work: the template always has these properties and methods available, regardless of which transaction type it is rendering.

Basic Debugging

Two tools tell you everything about a claim transaction: the Network tab and the Console. Click ▶ to step through.

Claim transaction bugs fall into two categories: the transaction fails to start (the screen never opens), or the transaction starts but misbehaves (wrong data, save fails, screen errors). The Network tab diagnoses the first; the Console diagnoses the second.

Basic transaction debug procedure — click ▶

Click to step through
1

Open Chrome DevTools — F12

Open the Network tab and filter by api/claims. Clear existing entries. Now trigger the transaction (click Amend, Close etc.).

2

Find the startXxx call

Look for a call matching the pattern /XuberHTMLApi/api/claims/Start[Mode]ClaimsTransaction e.g. StartAmendClaimsTransaction. This is always the first call when a transaction opens.

3

Check the status code

200 — transaction started, transactionId in the response. 400 — business rule violation (claim locked, authority issue). Check the Response tab for the errorMsg. 401 — session expired, user must log in.

4

Check the Console for debugOnInit

Every transaction component calls this.xuLoggerService.debugOnInit(this.constructor.name) in ngOnInit(). This logs the component class name. If you see it, ngOnInit ran. If you do not see it, the component never mounted — check the routing.

5

Trace subsequent API calls

After the start call, watch for calls using the transactionId in their query params. These are the screen data loads. A failure here means the transaction started but the screen data could not be fetched.

Quick Check — Transaction Won’t Open
A user clicks “Close Claim” and the screen never appears. The Network tab shows StartCloseClaimTransaction returning 400. The Response body contains "Outstanding reserve must be zero before closing". What is happening?
✅ Correct! A 400 from a Start transaction call almost always means the backend correctly rejected the request due to a business rule. The error message tells you exactly what the user needs to fix before proceeding. The HTMLUI should be surfacing this message — if it is not, the error handling in the UI component needs attention.
