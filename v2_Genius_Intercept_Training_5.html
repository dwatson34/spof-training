Step 1 — Download

Intercept (third-party software, requires library ST400OBJ54 in the library list) connects to the Insure FTP mailbox using credentials stored in data area GGNLIRFTP. It retrieves all outstanding raw EDI data, maps it to iSeries buffer files according to the Entity Definition, and writes the data to the appropriate capture file. LIRMA messages are compressed flat files (DSIGNS format). ELASS messages use EDIFACT standard layouts. The Genius Bureau system separates the retrieved records into different buffer files ready for the next step.

Programs: GBDI03 (ILU initiate) · GBDE03 (ELASS initiate) · GBDL02/GBDL03 (LIRMA) · Intercept GE entity
If this fails: Check WRKACTJOB for the job stream subsystem. If stuck in submitted state, blank data areas GGNLIRDLJB and GGNLIRDLST to reset.

Key files created at each pipeline stage

Each stage writes to specific iSeries files. Knowing which file holds what tells you where to look when diagnosing a problem at any point in the pipeline.

Raw message data is held in bureau buffer files. A member is created per day's batch in UTNMCPP (Bureau Signings Capture File) and UTELCPP (Bureau Claims Capture File). These are the raw files before Genius has validated or mapped anything.
ZBO1DL01 — Bureau Closings Header (one record per closing, updated by GBCM01). Logical file ZBO1DL04 is the primary access path for the OPNQRYF. ZBO1DL05 provides the instalment access path.
UTKBREL4 — Bureau Claims equivalent. One record per claim message. GBKM01 reads and updates this file.
GBCM00 creates ZBO1WKP, ZBO2WKP and UTCIWKP in QTEMP. GBKM00 creates UTKBWKP and UTKFWKP. These are session-scoped — cleared on entry and exit. If you see these files in QTEMP, an On-line Edit session is active (or ended abnormally).
Tracks how many closings remain to be processed per member (field BORHQY). GBCM01 decrements this count each time a closing is successfully processed (subroutine FBDEBO). GBKU02 can adjust the counts if the file gets out of sync. This file drives the Member Status Maintenance screen count.
GGNBURMSGF holds message text and default severity. UTMGREP holds user-adjusted severities and tolerances. Bureau validation uses UTMGREP. The on-line edit screen shows GGNBURMSGF severity. If they differ, the displayed severity will not match what actually blocks processing — a common source of confusion. Maintain via LIRMA menu or ELASS menu → Parameter Maintenance → Message Severity/Tolerance.
Common mistake: Jumping to On-line Edit before confirming downloads ran. If downloads did not run or failed, work files ZBO1WKP and ZBO2WKP are empty and GBCM01 shows no records. Always check WRKACTJOB for the download jobs first.

Bureau Closings On-line Edit — Deep Dive

Five tabbed sections: GBCM00 session setup, selection screen fields, the closings list, the edit screen, and the severity system

Bureau Closings On-line Edit is the main daily interface. GBCM00 (a CL program) builds the session environment before any screen appears. Understanding GBCM00 explains what happens when processing fails mid-way through.

What GBCM00 does before the screen appears

GBCM00 is called by the ILU or LIRMA menu with &SYC2 (PS=LIRMA, IL=ILU) and &SYSB (subsystem code). It runs entirely before the user sees anything.

1
Create/clear work files in QTEMP
ZBO1WKP, ZBO2WKP, ZBO2WKL0, ZBO2WKL1, UTCIWKP
CHKOBJ tests each file; CPYF with CRTFILE(*YES) creates if missing; CLRPFM clears. ZBO2WKP needs logical files ZBO2WKL0/ZBO2WKL1 via CRTDUPOBJ. If either logical is missing, the physical is rebuilt from scratch. This is why Bureau files appear in QTEMP during a session.
2
Start commitment control
STRCMTCTL LCKLVL(*CHG) NFYOBJ(*NONE)
Lock level *CHG holds records read with intent to update under commitment. Protects ZBO1DL01 and FUTBOREL0 from partial updates. If the session ends abnormally, MONMSG RPG9001 issues ROLLBACK.
3
Override files to QTEMP and set locking
ZBO1DL04 overridden with *SHRUPD SHARE(*YES)
Five OVRDBFs redirect work files to QTEMP. ZBO1DL04 gets RCDFMTLCK(@O1DL04A *SHRUPD) and SHARE(*YES) — shared update locking allows other users to read while someone edits. UTO0REP gets WAITRCD(*IMMED) to avoid waiting on a locked report file.
4
Call GBCM01
CALL GBCM01 PARM(&SYC2 &SYSB)
GBCM01 reads data areas, sets up the selection screen and runs until the user exits. GBCM00 waits here.
5
Error handling — MONMSG RPG9001
ROLLBACK, send BUR0001, call GBUT21 to print messages
If GBCM01 ends with RPG9001: ROLLBACK undoes all uncommitted changes. SNDPGMMSG sends BUR0001 to GGNBURMSGF. CALL GBUT21 receives and prints all program messages. BUR0001 in a joblog is the signature of this path. Check GBUT21 spooled output for the actual cause.
6
Cleanup — always runs on exit
ENDCMTCTL, CLRPFM, DLTOVR, RCLRSC
Whether normal or error: ENDCMTCTL, CLRPFM work files, DLTOVR all overrides, CLOF ZBO1DL04, RCLRSC. Guarantees clean state for the next session.

The severity system

Severity ≥ limit = Error (blocks processing). Severity < limit = Warning. Typically 30. View: WRKDTAARA UTTPRCA4. Do not raise without understanding which messages are blocking.
GGNBURMSGF = default severity (shown on screen). UTMGREP = user-adjusted severity (used by validation). If they differ, the displayed severity does not match what blocks processing. Maintain via bureau menu → Parameter Maintenance → Message Severity/Tolerance.
One critical error triggers several related ones. UTD0951 (claim not found) also raises: "Claim Section must be selected", "Invalid Loss Advised Date", etc. Resolve highest severity first — others clear automatically.

Severity reference

99Critical. UTD1310, UTD1410, UTD0011. Cannot be overridden. 50–77Severe. UTD0386, UTD0387, UTD1010, UTD0339. 30–49Error at limit 30. UTD0951 (40), UTD1130 (40), BUR0011 (40). 10–29Warning at limit 30. BUR0010 (15), BUR0016 (10). 1–9Informational. BUR9995 (1).
If messages block unexpectedly: check UTTPRCA4 (the limit) AND UTMGREP (the severities). Either could have changed.

GBCM11, Missing Closings and Error Message Reference

The OPNQRYF filter logic, three interactive diagnostic scenarios, and a clickable explorer for the most important Bureau error messages

GBCM11 is called every time the closings list needs building. It takes 14 parameters and assembles an OPNQRYF string. Knowing its logic means you can answer "why isn't this closing showing?" without guessing.

GBCM11 complete filter logic (QCLR009)

GBCM11 — filter assemblyCL
/* Always first: */
O1SYC2 = "PS" & BOSYSB = "SG"

/* Date (if entered): */
& O1FGTD = [CYMD date]

/* References — wildcard or exact: */
* in BORF → O1BORF = %WLDCRD("ABC*")
no *      → O1BORF = "exact value"
/* Same for MBRF, MBCO, TRRF */

/* Type flags — N means EXCLUDE: */
PRFQ=N → O1CLOT != "P"  Premiums
CMFQ=N → O1CLOT != "C"  Claims
TYFQ=N → O1CLOT != "T"  Treaties
FDFQ=N → O1CLOT != "F"  FDOs

/* Review: */
RVFQ=Y & NRFQ=N → O1VUFQ = "Y"
RVFQ=N & NRFQ=Y → O1VUFQ != "Y"

/* Deleted: */
RCFG='D' → O1SSCD != "D"

/* ILU product code (CR023662): */
MAPC != blank:
  JOIN ZBO1DL04 to ZUMADL10
  ON O1MBRF = MAPORF
  WHERE MAMAPC = "[code]"
N means exclude, not include. Claims=N excludes Claim-type records. Claims=Y does not add a filter — Claims are simply not excluded.

ZBO1DL04 key fields

O1SSCD — Status Code

blank=Open   D=Deleted   U=Processed
SFL: blank shows nothing, D="*** DELETED ***", U="* PROCESSED *" or "* GGI TRN CRTD*"

O1CLOT — Closing Type

P=Premium   C=Claim   T=Treaty   F=FDO
Set at Create Closings. Wrong type means it will not appear under the correct filter. Check: SELECT O1BORF, O1CLOT FROM ZBO1DL04 WHERE O1BORF='ref'

O1VUFQ — Review Flag

Y=Review   blank=Non-review
Set during Create Closings. Determines which Review/Non-review filter applies.

Bureau Claims, ELASS Rules, UCR Matching and Downloads

Four tabbed sections: GBKM vs GBCM, mandatory ELASS processing order, step-by-step UCR fixing, and download failure diagnosis

Bureau Claims mirrors Closings in structure but handles ELASS and CLAMS loss advices. The ELASS record type sequence and UCR matching rules are the most operationally important things to know — getting them wrong creates issues that are time-consuming to resolve.

Tip: BUR1001 in a joblog = GBKM01 ended abnormally (Claims). BUR0001 = GBCM01 (Closings). Always identify the chain first.

Claims-specific behaviour

ELASS messages carry a CLASS status code: MAN=entered not reviewed; CAA=loss advice accepted; YES=payment accepted; FIL=file requested; INF=more info needed. Only CAA and YES should enter Genius. Other types appearing in Genius indicate a Bureau or Intercept configuration error.
01=First Advice (new claim, no payment). 03=First Advice and Settlement. 02=Subsequent Advice (update to existing). 04=Subsequent Advice and Settlement. Must be processed in sequence 01→03→02→04 per Transmission Date. Wrong order causes duplicate claims or broken UCR links.
Before processing any date, check Member Status Maintenance (option 11 from ELASS Bureau Menu). The date should show Claims Validated. Any other status means upstream pipeline steps have not completed — do not process that date.

ELASS processing sequence — mandatory order

From Bureau ELASS User Process v1 (Xchanging/AXA 2005). This is not a guideline.

ELASS Claims On-line Edit — Select
Transmission Date: 01/11/04 (one date at a time) Step 1: Record Type 01 First Advice Process all 01 records, return Step 2: Record Type 03 First Advice+Settlement Process all 03 records, return Step 3: Record Type 02 Subsequent Advice Process all 02 records, return Step 4: Record Type 04 Subsequent+Settlement Process all 04 records, return Step 5: Record Type (blank) catch remaining Then process LIRMA claims for same date

Why the sequence matters

01 creates the initial claim structure. 03 also creates a claim but with settlement. Processing 03 first creates a claim with only the settlement portion, losing the loss advice context. 01 first establishes the claim, then 03 adds the settlement.
02/04 update an existing claim via UCR. If processed before 01/03, there is no claim to link to — UTD0951 fires for every subsequent advice. Requires manual UCR correction on every affected record.
Process all ELASS for a date before LIRMA claims for that date. When multiple dates present, process oldest first. Later-date subsequent advices cannot link to first advices that have not yet been processed.

UCR matching — fixing UTD0951

The Unique Claim Reference links every ELASS message to a Genius claim. When the link breaks, UTD0951 fires and cascading errors follow.

In Genius: Claim Broker Reference 2 — two fields concatenated: Loss Broker Ref 2 + Claim ASC Currency. Genius searches ZKFADL13 (Claim Master) using the UCR from the ELASS message. No match = UTD0951.
1. Note UCR and Policy Reference from UTD0951 message.
2. Genius → Underwriting → Policy → Enquiry. Enter reference.
3. KT enquiry: identify the correct claim.
4. Claims Menu → Claims Maintenance → Amend claim (1/02).
5. Enter UCR in Claim Broker Reference 2 (Loss Broker Ref 2 + Claim ASC Currency).
6. Return to ELASS On-line Edit. Amend item, revalidate. Process normally.

Configuration, Parameters and Setup

Key data areas, tolerance parameters, automatic processing flags and the GGNBURMSGF vs UTMGREP sync issue

Genius Bureau has a substantial configuration layer. Many issues that appear to be software problems are actually configuration issues. Knowing what to check avoids unnecessary escalation.

Key parameters and data areas

Maintained via Genius Housekeeping → Environment Control → Work with Parameters → Group *Bureau, or directly via WRKDTAARA.

UTTPRCA4=Bureau Closings Error Limit (typically 30). UTTPRCA5=Bureau Claims Error Limit. Messages at or above severity block processing. View/change: WRKDTAARA UTTPRCA4. Do not raise without understanding which messages are blocking and why.
Signed Line % Tolerance, Signed Slip Order % Tolerance, Share of Whole % Tolerance. All typically 10%. Affect UTD1102 (signed line differs from written). Adjust these tolerances after discussion rather than raising the error limit.
Three-char flags (Download/Create/Validate). N=manual, Y=auto. UTPSRSA3=LIRMA, UTPSRSA9=ELASS. NNN=fully manual. YYN=Download+Create auto. YYY=fully automatic. Only automate steps confirmed stable. Endurance started NNN and moved to YYN.
Library names for MULTINET/Intercept concatenated, e.g. ST400OBJ54ST400PTF54ST400V54GL. Set by GBDE04/GBDI04 before starting the download job stream. Must be updated when MULTINET is upgraded to a new version.
Mailbox profile, password, IP address and path (e.g. YAXACsUk rCMyP3Bv 10.137.250.2 AXACSA47.AXACS001/To). Check WRKDTAARA GGNLIRFTP. Must be updated if Insure changes the mailbox IP, credentials or path.
Track current download job name and status. Blank these to reset a stuck download: WRKDTAARA GGNLIRDLJB then change to blanks. Same for GGNLIRDLST. Confirm Job Stream Subsystem is active before resubmitting.
GGNBURMSGF holds default severities (what the on-line edit screen shows). UTMGREP holds user-adjusted severities (what validation actually uses). If someone directly edits GGNBURMSGF without updating UTMGREP, users see one severity but validation uses another.
