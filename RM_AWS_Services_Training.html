Amazon S3 — Simple Storage Service

How Xuber uses S3 for document storage, backups and static assets

S3 stores objects (files) in buckets. In Xuber, S3 holds claim documents, policy attachments, DB backup archives, and application logs. Understanding S3 is essential for backup/restore and document workflows.

Xuber S3 bucket layout

xuber-documents-prod

Claim & Policy documents

PDF attachments, photos, correspondence. Objects keyed by claims/{claimId}/{docId}.pdf

xuber-backups-prod

Database backups

Nightly SQL Server .bak files. 30-day retention via S3 Lifecycle policy. Encrypted with AES-256.

xuber-logs-prod

Application logs

CloudWatch Logs exported to S3 for long-term retention and compliance. Gzip compressed.

Key S3 operations

List bucketS3 Console → Buckets → Click bucket name. Lists all objects with size and last modified date.
Download objectClick object → Download, or use Actions → Download. For bulk: select multiple → Actions → Download.
Check lifecycleBucket → Management tab → Lifecycle rules. Shows retention and transition policies.
Verify encryptionBucket → Properties tab → Default encryption. All Xuber buckets must show AES-256 or KMS.

Amazon EC2 — Xuber Servers

Managing the virtual machines that run Xuber application and database tiers

Xuber runs on EC2 instances — virtual machines in AWS. The RM team must be able to start, stop, check status and connect to these instances for maintenance and incident response.

xuber-app-prod

Application servers

Windows Server 2019, m5.2xlarge. Runs the Xuber application tier. 2 instances behind ALB for HA.

xuber-db-prod

Database server

Windows Server 2019, r5.4xlarge. SQL Server 2019 Enterprise. Single instance — DB backups critical.

xuber-iseries

iSeries gateway

Linux, c5.xlarge. Hosts the iSeries connectivity layer for AS400 communication.

xuber-bastion

Bastion host

Amazon Linux, t3.micro. The jump server — all RDP/SSH to Xuber instances goes through the bastion.

⚠️
Never connect directly to production EC2

Always use the bastion host. Direct Security Group rules block RDP/SSH from the internet. Access is: VPN → Bastion → Target instance.

EC2 Console: EC2 → Instances → Filter by Name tag "xuber". Green circle = Running. Stop/Start via Instance State menu. Always check CloudWatch metrics before stopping.

Concept 3

Security Groups

Controlling network access to Xuber EC2 instances with port-level firewall rules

A Security Group is a stateful firewall attached to an EC2 instance. It defines which IP addresses and ports can connect inbound, and which outbound connections are allowed. Wrong rules = production outage or security breach.

Xuber Security Group rules

sg-xuber-app

Application tier

Inbound: Port 443 (HTTPS) from ALB only. Port 3389 (RDP) from bastion only.
Outbound: Port 1433 to sg-xuber-db.

sg-xuber-db

Database tier

Inbound: Port 1433 (SQL) from sg-xuber-app only. Port 3389 (RDP) from bastion only.
Outbound: Port 443 to S3 VPC endpoint.

sg-xuber-bastion

Bastion host

Inbound: Port 22 (SSH) from DXC office IPs and VPN CIDR only.
Outbound: Port 3389 to xuber-app and xuber-db.

⚠️
Never add 0.0.0.0/0 rules

Opening a port to all IPs on a production Security Group is a critical security incident. Always scope rules to specific IP CIDRs or other Security Group IDs.

To check rules: EC2 → Security Groups → Find by name → Inbound/Outbound rules tabs. Changes take effect immediately — no restart needed.
Troubleshooting: If an application can't connect to the DB, check sg-xuber-app outbound port 1433 is allowed to sg-xuber-db. If a user can't RDP, check their IP is in sg-xuber-bastion inbound rule.

Concept 4

IAM — Identity & Access Management

Users, roles and policies controlling Xuber AWS access

IAM controls who can do what in the Xuber AWS account. Every person and every application has an IAM identity with specific permissions. Principle of least privilege — only the minimum access needed.

IAM concepts

Users

Human identities

One IAM user per person. Used for Console access and CLI. Must have MFA enabled on all Xuber accounts.

Roles

Service identities

EC2 instances use IAM Roles (not user credentials) to access S3, CloudWatch etc. Roles are assumed temporarily.

Policies

Permission documents

JSON documents defining Allow/Deny for specific AWS actions and resources. Attached to users or roles.

Groups

Collections of users

Xuber uses groups: xuber-admins, xuber-read-only, xuber-developers. Policies attached to groups, not individuals.

Xuber S3 read-only policy (example)JSON
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:ListBucket"
    ],
    "Resource": [
      "arn:aws:s3:::xuber-documents-prod",
      "arn:aws:s3:::xuber-documents-prod/*"
    ]
  }]
}
To check permissions: IAM → Users → Select user → Permissions tab. Or use IAM Policy Simulator to test a specific action before applying changes.

CloudWatch — Monitoring & Alarms

Monitoring Xuber health and responding to infrastructure alerts

CloudWatch collects metrics, logs and events from every Xuber AWS resource. The RM team uses it to monitor health, investigate incidents and respond to alarms before they become outages.

📈 Key metrics to watch

EC2: CPU >80% sustained, Memory >90%, Disk >85%
RDS: DatabaseConnections, ReadLatency, FreeStorageSpace
ALB: TargetResponseTime, HTTPCode_Target_5XX_Count

🚨 Xuber alarms

xuber-cpu-high: App server CPU >80% for 5 min → Notify RM team
xuber-db-disk: DB disk <20GB free → Page on-call
xuber-5xx: >10 HTTP 500s per minute → PagerDuty

📋 Log Insights queries

CloudWatch → Log Insights → Select /xuber/application. Query: fields @timestamp, @message | filter @message like /ERROR/ | sort @timestamp desc | limit 50

✅ Health check

CloudWatch → Dashboards → Xuber-Production. Shows all key metrics in one view. Check this first for any Xuber incident.

Responding to an alarm: 1) Open CloudWatch dashboard. 2) Identify the spiking metric. 3) Open relevant EC2 instance. 4) Check system logs. 5) Engage on-call DBA or app team as needed.
