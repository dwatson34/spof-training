Concept 1

What Is GLOBAL XLPro?

Understanding the platform and why insurers use it

GLOBAL XLPro is a specialized reinsurance platform. Think of it as a "transaction machine" for reinsured business—policies that an insurer has transferred to another party for risk management. Xuber Enterprise handles the front-end business operations, while XLPro handles the reinsurance backend.

Scenario: A Real-World Example
An insurance company issues a policy in Xuber. What happens next?

What XLPro Does

Type

Reinsurance Hub

Manages all reinsured policies, claims, and financial transactions. If Xuber issues a reinsured policy, XLPro tracks it from creation through settlement.

Type

Data Integration Point

Xuber and XLPro talk to each other automatically. When something changes in Xuber (a policy update, a claim), XLPro gets notified and syncs the data.

Type

Reliability Engine

XLPro remembers everything. If Xuber is temporarily down, messages queue up and process when Xuber is back online—no data loss.

In The Stack

GLOBAL XLPro ← Reinsurance backend
Integration Layer ← Bridges the gap
Xuber Enterprise ← Your primary system
Xuber Messaging ← Event transport
Key Insight: Xuber doesn't "know about" XLPro—it just keeps running. The integration is the messenger between them.
▼ When would you actually need XLPro?

XLPro integration is needed when:

  • You broker reinsurance. Your company takes on reinsured business and must track it in a dedicated system.
  • You have dual-system operations. Both Xuber and XLPro run in your environment and must stay synchronized.
  • Regulatory requirements demand it. Reinsured business often has special reporting and compliance requirements.
  • You need separation of concerns. Xuber handles primary business; XLPro handles reinsured business—cleaner operations.

Concept 2

How Integration Works

The automated flow of data between Xuber and XLPro

The XLPro integration is two components working together: one on the Xuber side (listening for events) and one on the XLPro side (processing messages). Data flows automatically without manual intervention.

The Integration Flow

1

Policy Created in Xuber

A user creates a reinsured policy in Xuber Enterprise. The policy is marked as "reinsured" and saved to the database.

2

Event Published

Xuber Messaging broadcasts a "Policy Created" event to all listening systems, including the XLPro integration component.

3

Integration Captures Event

The XLPro integration listener on the Xuber server receives the event, extracts policy details, and formats them for XLPro.

4

Message Sent to XLPro

The formatted message is transmitted to the XLPro database. If the connection fails, the message queues and retries automatically.

5

XLPro Processes Message

The XLPro system receives the message and loads the policy into its database. The policy is now in both systems, synchronized.

Key Principle: Asynchronous & Reliable

Xuber doesn't wait for XLPro. It completes the policy transaction immediately. The integration happens in the background, reliably, even if XLPro is temporarily offline. No data is ever lost.

What Data Syncs?

Event Type

Policies

New, updated, renewed, or cancelled policies from Xuber automatically sync to XLPro's database.

Event Type

Claims

When a claim is created or modified in Xuber, XLPro is notified and updates its records.

Event Type

Financial Data

Premiums, payments, and settlements flow from Xuber to XLPro for financial reconciliation.

Requirements

What You Need

Prerequisites for XLPro integration deployment

Before deploying XLPro integration, your environment must have certain components in place. Think of this as your "pre-flight checklist"—without these, the integration won't work.

Xuber Environment

✓ Required

Xuber Enterprise

A fully operational Xuber Enterprise system must be installed and running on at least one server.

✓ Required

Xuber Messaging

The Xuber Messaging service must be active and properly configured. This is what carries events between systems.

XLPro Environment

✓ Specific Version

GLOBAL XLPro 2.8.30

XLPro must be version 2.8.30. Older versions may not be compatible; newer versions may have breaking changes.

✓ Required

SQL Server Database

An active SQL Server instance with the XLPro database installed and accessible from the Xuber environment.

Network & Access

✓ Required

Network Connectivity

Xuber servers must be able to reach the XLPro database server on port 1433 (or your custom SQL Server port). No firewall blocks.

✓ Required

Database Permissions

Service accounts running the integration must have read/write permissions on the XLPro and Xuber databases.

⚠️
Before You Deploy

Back up your databases. The integration modifies database schemas and cannot be easily reversed. Always have verified backups of both Xuber and XLPro databases before installing.

▼ How do I check if my environment meets these requirements?

Xuber Enterprise: Open your Xuber application. If you can log in and create a policy, Xuber is running.
Xuber Messaging: Check Windows Services for "Xuber Messaging" service. It should show "Running" status.
XLPro Version: In GLOBAL XLPro, go to Help → About. Verify version is 2.8.30 or compatible.
SQL Server Access: From the Xuber server, open SQL Server Management Studio and try to connect to the XLPro database server. If it connects, you're good.
Network Connectivity: From command line, run: telnet [XLPro-server-name] 1433. If it connects, the port is open.

Architecture

Integration Architecture

How all the pieces fit together in the bigger picture

The XLPro integration is part of a larger technology stack. Understanding where it sits helps you grasp how events flow through the system and why integration matters.

The Technology Stack

Xuber Environment (Your Primary System)
├─ Xuber Enterprise Server (where users work)
├─ Xuber Messaging Server (broadcasts events)
└─ XLPro Integration Components (listen and send)

XLPro Environment (Reinsurance Backend)
├─ GLOBAL XLPro Application
├─ SQL Server Database
└─ USM 6-9 Load Service (processes incoming messages)

The Bridge
└─ Integration Connection (network link, secure credentials)

Why This Architecture?

Separation of Concerns

Xuber handles primary business operations. XLPro handles reinsured business. Each system is optimized for its job, and they communicate through a clean integration layer.

Loose Coupling

Xuber doesn't wait for XLPro. It completes its work immediately. If XLPro is temporarily down, Xuber keeps running—messages queue and process when XLPro comes back.

Reliability

Using message queuing and persistent databases means no data is ever lost. Even in a system failure, all transactions are recoverable and retryable.

Scalability

As transaction volume grows, you can add more servers, upgrade databases, or tune message processing without changing the core architecture.

A Message's Journey

Example: A policy event
SQL
-- In Xuber Enterprise:
INSERT INTO Policy (PolicyRef, EffectiveDate, Status)
VALUES ('POL-2024-00542', '2024-10-01', 'Active');
-- This INSERT triggers a message to Xuber Messaging

-- Xuber Messaging broadcasts:
Event: 'PolicyCreated'
Payload: { policyRef: 'POL-2024-00542', ... }

-- XLPro Integration listener receives this and:
INSERT INTO xlpro_staging_table
VALUES (...payload from message...)

-- USM 6-9 Load processes the staging table:
INSERT INTO XLPro.dbo.Policy
VALUES (...data from staging...)

-- Policy is now in both Xuber AND XLPro ✓
Design Principle: The integration is "dumb"—it doesn't make decisions. It captures, transforms, and delivers. Business logic stays in Xuber and XLPro. The integration is just the messenger.
