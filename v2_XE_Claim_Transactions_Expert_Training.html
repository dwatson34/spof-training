Reserve — ClaimTransactionSource.Reserve

A Reserve entry sets aside funds to pay a future claim amount. The R&P base class provides newRandPCommand(ClaimTransactionSource.Reserve) to initiate a reserve entry. The reserve panel allows entry of amounts by claim detail, with sub-types for Reinsurance, Coinsurance, and ReinsuranceOnCoinsurance. Discarding a reserve calls discardReserve() in the base class.

The ClaimTransactionSource enum

Four source types from real source:
ClaimTransactionSource.Reserve
ClaimTransactionSource.Payment
ClaimTransactionSource.RecoveryReserve
ClaimTransactionSource.RecoveryReceipt

Reserve and RecoveryReserve both trigger sub-group calculations (Reinsurance, Coinsurance, ReinsuranceOnCoinsurance). Payment and RecoveryReceipt have a simpler calculation path.
newRandPCommand(ClaimTransactionSource) in the main base class initiates the R&P entry process for the given type. It calls executeRandPTransaction() which builds the context and opens the R&P entry panel. The switch statement dispatches to the correct panel type based on the source enum.
The main base class has four separate discard methods: discardReserve(), discardPayment(), discardRecoveryReserve(), discardRecoveryReceipt(). Each calls the corresponding service method to roll back the partial entry. They are wired to the Discard buttons in the R&P panels.

XuCurrentFinancialGroupPanel is the component that displays the current financial totals panel within a claim transaction. It extends XuRandPClaimTransactionBase and receives its context from the parent transaction component via @Input().

The @Input() parent reference pattern

The financial panel receives the entire parent transaction component as an @Input(). This gives it access to all the parent’s properties and methods without service injection. The parent sets: <xu-current-financial-group-panel [claimTransactionComponent]="this"></xu-current-financial-group-panel>. This tight coupling is a deliberate Xuber pattern for child panels that are specific to claim transactions.

When debugging the financial panel: If it appears blank or shows wrong data, check the parent is correctly passing [claimTransactionComponent]="this". The panel cannot function without its parent reference.

AmountType controls what data loads

The amountType property determines which financial data the panel loads. AmountType.Reserve loads reserve amounts. AmountType.RecoveryReserve loads recovery reserve amounts. Both use the same getCurrentFinancialDetailDetail() method with a different enum value. The transactionId comes from the parent component via claimTransactionComponent.transactionId.

Three currency contexts

Xuber handles three simultaneous currency contexts in financial panels. originalCurrencyCode is the currency the claim was written in (from the policy). accountingCurrencyCode is the company’s functional currency for ledger entries. selectedCurrency is what the user has chosen to view. xuDecimal.formatIntoCultureGroupSeparator() formats amounts for display using the correct decimal and thousands separator for the user’s locale.

getCurrentFinancialDetailDetail(
  transactionId: any,
  amountType: AmountType

      transactionId, amountType

    .then((data:

The CurrentFinancialDetail model

The response is typed as CurrentFinancialDetail from xuCurrentIncurredAndRecoveryModel. This model carries the complete financial state including amounts by sub-group, all three currency codes, and the breakdown by claim detail. When debugging a financial panel showing wrong amounts, check the Network tab for the getCurrentFinancialDetailDetail call and verify the response shape matches this model.

AfterViewChecked & xuCache

Click each tab to understand why amend and display implement AfterViewChecked, and how xuCache stores layer claim context.

AfterViewChecked — XuAmendClaimTransactionComponentTypeScript
export class
  XuAmendClaimTransactionComponent
  extends
    xuClaimsTransactionComponentBase
  implements AfterViewChecked {

  ngAfterViewChecked() {
    if (!this.navigationButtonsAdded) {
      if (this.navigationButtons !==
        undefined) {
          this.addCustomHooks();
          this.navigationButtonsAdded
            = true;
          this.changeDetectorRef
            .detectChanges();
      }
    }
  }
}

Why ngAfterViewChecked?

AfterViewChecked fires after every change detection cycle once the view is stable. Amend and display use it to detect when the navigation buttons (from the shared template) become available in the DOM — signalled by this.navigationButtons !== undefined. Only then does it call addCustomHooks() to attach custom behaviours to those buttons, sets the navigationButtonsAdded flag to prevent re-execution, and calls changeDetectorRef.detectChanges() to trigger a UI refresh.

Why not ngAfterViewInit? The navigation buttons may not be rendered immediately in ngAfterViewInit because they depend on async data. AfterViewChecked keeps checking until they appear — but the navigationButtonsAdded guard ensures this only runs once.

xuCache — the client-side cache

xuCache is Xuber’s client-side key-value store. The amend component uses it to check whether this amend session was preceded by a layer claim creation. The key is constructed from the string prefix plus the transactionId. This ties the cache entry to a specific transaction session. If a layer claim virtualTransactionId exists in cache, the amend component knows to broadcast a refresh event when the tab closes.

Pattern: cache key = descriptive prefix + unique ID. This namespacing prevents collision with other cache entries across components.
xuEventPubSub.broadcast — real sourceTypeScript
// Broadcast in amend tab close:
window.parent.xuEventPubSub
  .broadcast(
    Xuber.eventStore
      .refreshClaimLayersGrid
      FromCreateClaim,
    { transactionId:
        this.transactionId }
  );

// Listening component receives:
window.parent.xuEventPubSub
  .on(
    Xuber.eventStore
      .refreshClaimLayersGrid
      FromCreateClaim,
    (data) => {
      this.refreshLayersGrid(
        data.transactionId
      );
    }
  );

The publish-subscribe pattern

xuEventPubSub is Xuber’s event bus on the parent frame. Events are identified by named constants in Xuber.eventStore. The broadcast carries a payload object. Any component that has registered a listener via .on() receives the event. In this case: when the amend transaction closes after a layer claim creation, it broadcasts so that any listening grid component knows to refresh its layer claim data.

The amend transaction handles the layer claim data within the session. The layers grid (in the parent frame) needs to refresh after the session is fully closed and the data committed — not while the amend is still in progress. Broadcasting on tab close ensures the grid only refreshes when the complete transaction is done and data is stable.

Layer Claims

Click ▶ to step through the full layer claim creation and amend sequence, including the xuCache and broadcast handshake.

XuCopyMasterClaimToLayerClaimTransactionComponent creates a layer claim by copying a master claim into the XL/excess of loss layer structure. It is the most complex transaction component — it creates a claim AND then immediately opens amend, using xuCache to pass context between the two sessions.

The layer claim sequence — click ▶

Click to step through
1

XuCopyMasterClaimToLayerClaimTransactionComponent starts

ngOnInit sets transactionMode = xuTransactionMode.create. This is a copy transaction — isCreateTransaction returns false. startNewTransaction() calls startCopyMasterClaimToLayerClaimTransaction() and returns a XuDeferred resolving with the new claim’s transactionId.

2

virtualTransactionId is generated

XuUUIDGenerator.generateUUID() creates a virtualTransactionId. This is stored in xuCache under the key 'layerClaimVirtualTransactionId_' + transactionId. This links the layer creation session to the amend session that follows.

3

After save: openAmendTransaction()

showTransactionCompleteDialog() calls openAmendTransaction(). This builds the amend URL for the newly created layer claim and opens it via window.parent.overrideTab(). The same tab now shows the amend transaction.

4

Amend reads virtualTransactionId from cache

XuAmendClaimTransactionComponent.startNewTransaction() reads xuCache.get('layerClaimVirtualTransactionId_' + transactionId). If found, it knows this amend session followed a layer claim creation and sets up accordingly.

5

Tab close broadcasts refresh event

When the amend tab is closed, onTabCloseClicked() checks the cache. Finding the virtualTransactionId, it broadcasts Xuber.eventStore.refreshClaimLayersGridFromCreateClaim to the parent frame so the layers grid refreshes to show the new layer claim.

Layer claim component — key real codeTypeScript
startNewTransaction() {
  let defer =
    new XuDeferred<any>();
  let virtualTxnId =
    XuUUIDGenerator.generateUUID();

  xuCache.set(
    'layerClaimVirtualTransactionId_'
    + this.transactionId,
    virtualTxnId
  );
  this.xuClaimsTransactionService
    .startCopyMasterClaim
    ToLayerClaimTransaction(
      this.claimReference,
      this.claimStage,
      this.masterClaimHeaderId
    )
    .then(data => {
      defer.resolve(data.transactionId);
    });
  return defer.promise;
}
The three-component handshake:
1. XuCopyMasterClaimToLayerClaim creates the layer and stores virtualTransactionId in cache
2. XuAmendClaimTransaction reads cache and sets up layer context
3. On close, amend broadcasts to the parent event bus
4. The layers grid listener refreshes

This is the most complex interaction pattern in the claims transaction framework. It spans three components, two sessions, the cache, and the parent event bus.

Adding a New Transaction Type

Click ▶ to step through the complete 8-step process. Miss any step and the TypeScript build fails.

Adding a new claim transaction type to the Xuber HTMLUI requires following the established pattern exactly. The TypeScript compiler enforces most of these steps — but not all. The ones it does not enforce are where dangerous mistakes happen.

The complete process — click ▶

Click to step through
1

Add the new mode to xuTransactionMode enum

Add a new value to the xuTransactionMode enum. This is the type identifier all framework code will use. The build will not fail yet — enums accept new values without breaking existing usage.

2

Add the start method to XuClaimsTransactionService

Following the exact Xuber service pattern: private static ApiPath constant, method with params object, xuWebApiManager.get(url, params).then(r => { xuLoggerService.debugResponse(url); return r; }).

3

Create the component class file

New file in feature/claims/transactions/. Extend xuClaimsTransactionComponentBase. The TypeScript compiler immediately requires all 7 abstract methods — it will not compile until all are implemented.

4

Implement all 7 abstract methods

getComponentName(), isCreateTransaction, getHeaderTitle(), getTabTitle, startNewTransaction() (using XuDeferred), showTransactionCompleteDialog(), saveButtonHandler(). TypeScript enforces all 7.

5

Set the correct transactionMode in ngOnInit

Add ngOnInit(): call xuLoggerService.debugOnInit(this.constructor.name), set this.claimStage = ClaimStage.Claim, call this.IntitateDefaultSection(), set this.transactionMode = xuTransactionMode.yourNewMode.

6

Add @Component decorator with the SHARED template

Selector: xu-your-new-transaction. templateUrl: the shared common/transactions/components/xuTransaction.component.html. encapsulation: ViewEncapsulation.None. standalone: false.

7

Declare in the claims module

Add to the declarations array in claims.module.ts. Without this, Angular will not recognise the selector in any template and will silently render nothing.

8

Add to XuClaimTransactionUrlBuilder

Add a typed URL builder method buildYourNewTransactionUrl(). This gives all callers a typed, safe way to construct the navigation URL for the new transaction. Never hard-code transaction URLs inline — always use the URL builder.

Expert Scenarios

Expert Scenario Challenges

Four complex, multi-layer situations requiring knowledge from all three levels.

Expert Scenario 1 — Financial Panel
XuCurrentFinancialGroupPanel shows no data. The Network tab shows no getCurrentFinancialDetailDetail call was made. ngOnInit is confirmed running via debugOnInit. What is the most likely cause?
✅ Correct! The financial panel depends entirely on the claimTransactionComponent @Input for its transactionId. If the parent is not passing it, this.claimTransactionComponent.transactionId will throw or be undefined — causing the amountType condition to fail before calling the API. Check [claimTransactionComponent]="this" in the parent template.
Expert Scenario 2 — AfterViewChecked
In XuAmendClaimTransactionComponent, addCustomHooks() is being called on every change detection cycle, causing performance problems. What is the fix?
✅ Correct! The navigationButtonsAdded flag exists specifically to prevent addCustomHooks() from running more than once. If it is not being set to true after the first execution, ngAfterViewChecked will call addCustomHooks() on every change detection cycle. This is the exact guard the real source uses.
Expert Scenario 3 — Layer Claims
After creating a layer claim and completing the amend transaction, the layers grid in the parent frame does not refresh. The layer claim was created correctly. What is wrong?
✅ The refresh depends on two things happening correctly: (1) the copy component storing the virtualTransactionId in xuCache, and (2) the amend component finding it in xuCache during onTabCloseClicked() and broadcasting. If either fails silently, the grid does not refresh. Add console.log to both xuCache.set() and the onTabCloseClicked broadcast to trace the flow.
Expert Scenario 4 — New Transaction Type
A new transaction component builds and runs. The user can open it. But navigating to it from other screens fails — the URL is malformed. Which step was skipped?
✅ Correct! The URL builder step is the one TypeScript does not enforce. All callers building the URL manually are a maintenance risk and a source of malformed URLs. XuClaimTransactionUrlBuilder.buildYourNewTransactionUrl() must be added so all navigation to the new transaction type goes through a single, tested, typed URL construction path.
