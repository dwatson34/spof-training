Concept 1

Xuber SQL Server Architecture

Databases, instances and nightly maintenance jobs

Xuber uses SQL Server 2019 on AWS RDS. The RM team manages the databases, backup integrity and performance. AWS handles OS patching and high availability.

Xuber SQL Server databases

XuberCore

Main application database

All policies, claims and configuration data. Approximately 200 GB. The primary target for all backup and restore operations.

XuberReporting

Reporting database

Read replica used by BI reports. Refreshed nightly from XuberCore. Never used for writes.

XuberAudit

Audit trail database

Immutable compliance log. Retained 7 years. Never delete or modify records from this database.

Nightly SQL Agent jobs

Sunday 01:00

Full backup

Complete copy of XuberCore to S3. Takes approximately 45 minutes. Alerts on failure.

Mon-Sat 01:00

Differential backup

Changes since last full. Takes 5 to 10 minutes. Much smaller file than full.

Every 15 min

Transaction log backup

Runs around the clock. Enables point-in-time recovery to within 15 minutes of any failure.

RDS advantage: AWS RDS handles SQL Server patching and Multi-AZ high availability. The RM team focuses on data-level operations.

Concept 2

SQL Server Backup Types

Full, differential and transaction log backups - how they chain together

The three backup types work together to give point-in-time recovery. You must apply them in the correct order. Missing one breaks the chain.

Full Backup

Complete database copy

Runs every Sunday at 01:00. Approximately 200 GB for XuberCore. The starting point for any restore. You always need this first.

Differential Backup

Changes since last full

Runs Monday to Saturday at 01:00. Grows through the week. Apply after the full to reach a specific day.

Transaction Log Backup

Every transaction

Runs every 15 minutes all day. Applied in chain after full and differential. Enables point-in-time recovery to the exact minute.

Recovery sequence: Full backup first, then differential for the target day, then transaction logs in order up to the target time. Always this order. Never skip a step.
RPO - Recovery Point Objective: Maximum data loss is 15 minutes - the transaction log backup frequency.
RTO - Recovery Time Objective: Approximately 2 hours to restore XuberCore from a full backup plus logs.
⚠️
Failed backup job equals a P1 incident

Escalate immediately. Do not wait for the next scheduled run. Each missed backup increases potential data loss.

Concept 3

Restore Procedures

Point-in-time recovery - the exact sequence. Never deviate from this order.

A database restore is the highest-stakes operation in RM. Follow this sequence exactly. Deviating from the order causes incomplete restores that appear to work but have data gaps.

Point-in-time restore sequenceT-SQL
-- Step 1: Full backup WITH NORECOVERY
RESTORE DATABASE [XuberCore]
FROM DISK = 's3://xuber-backups/full.bak'
WITH NORECOVERY, STATS = 10;

-- Step 2: Differential WITH NORECOVERY
RESTORE DATABASE [XuberCore]
FROM DISK = 's3://xuber-backups/diff.bak'
WITH NORECOVERY;

-- Step 3: Log files in order
RESTORE LOG [XuberCore]
FROM DISK = 's3://xuber-backups/log.bak'
WITH NORECOVERY;

-- Final log: RECOVERY brings DB online
RESTORE LOG [XuberCore]
FROM DISK = 's3://xuber-backups/log2.bak'
WITH RECOVERY,
  STOPAT = '2025-01-15 14:37:00';

-- Verify integrity
DBCC CHECKDB ([XuberCore]);

Restore sequence steps

!

Get CAB approval first

All production restores require emergency CAB approval. Document the incident reference before starting.

1

Stop the application

Stop Xuber API services. Verify no active database connections. Restoring with active connections causes failure or data inconsistency.

2

Restore WITH NORECOVERY

Apply full, then differential, then logs - all WITH NORECOVERY except the final log which uses WITH RECOVERY and STOPAT.

3

Verify and bring online

Run DBCC CHECKDB. Verify record counts. Restart application services. Confirm Xuber is functioning before closing the incident.

Concept 4

Environment DB Refresh

Refreshing UAT or TEST from production data - mandatory data masking applies

A DB refresh copies production data into a non-production environment for realistic testing. Data masking is legally required before any non-production team can access the refreshed database.

1

Raise change request

Confirm with the test team that UAT is not in active use. Agree the refresh window - usually weekend.

2

Snapshot the target first

Backup the current UAT database before overwriting. This gives a rollback option if the refresh fails midway.

3

Restore production backup to UAT

Use the most recent Sunday full backup. Restore to the UAT SQL Server instance WITH RECOVERY - no further logs needed.

!

Run data masking scripts - MANDATORY

Execute XuberMasking_v3.sql. This replaces real names, NI numbers, addresses and bank details with fake data. Verify with the GDPR check query before proceeding.

5

Verify and notify

Update connection strings. Confirm login works. Send confirmation email with data cutoff date. Log in the change record.

🔒
GDPR - Data masking is not optional

Running unmasked production personal data in a test environment is a data breach. The masking script must run and the GDPR check query must return zero before the refresh is signed off.

Concept 5

Daily Monitoring and Health Checks

The queries and checks the RM team runs every morning for Xuber SQL Server

Proactive monitoring catches problems before users notice them. These checks take 5 minutes and form the morning SQL Server health check.

Daily health check queriesT-SQL
-- Check for blocking
SELECT blocking_session_id,
  session_id, wait_type,
  wait_time/1000 AS wait_sec
FROM sys.dm_exec_requests
WHERE blocking_session_id > 0;

-- Failed SQL Agent jobs last 24h
SELECT j.name,
  h.run_date, h.message
FROM msdb.dbo.sysjobhistory h
JOIN msdb.dbo.sysjobs j
  ON h.job_id = j.job_id
WHERE h.run_status = 0
  AND h.run_date >= CONVERT(
    int, GETDATE()-1, 112);

-- Database file space
SELECT name,
  size*8/1024 AS size_MB
FROM sys.database_files;

When to escalate

Blocking chain over 30 seconds

Identify the head blocker session. Restart the Xuber app service first before killing the SQL session directly.

Backup job failed

Treat as a P1 incident. Fix the cause and manually run the backup before the next scheduled window.

Database file over 85 percent

Request an RDS storage increase proactively. At 100 percent the database goes read-only and Xuber stops working.
