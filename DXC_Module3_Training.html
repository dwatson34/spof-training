Concept 1

Xuber Codebase Tour

Key directories and files every Xuber HTMLUI developer needs to know

The Xuber HTMLUI repo follows a feature-module structure. Every domain area has its own module folder with components, services, and models.

xuber-htmlui/ (repo root)Structure
src/app/
  app-routing.module.ts  ← all routes
  core/                  ← interceptors, guards
  shared/                ← reusable components
  features/
    policy/              ← PolicyModule
    claims/              ← ClaimsModule
    lmm/                 ← LmmModule
angular.json             ← build config
proxy.conf.json          ← API proxy

Key conventions

Feature modules

One folder per domain

Each features/ folder: .module.ts, routing.ts, components/, services/, models/. Mirror this for new screens.

Core vs Shared

Know the difference

Core = singleton services (auth, interceptors). Shared = reusable UI components. Never import CoreModule twice.

environment files

Config per environment

API base URL and feature flags live in environment.ts (dev) and environment.prod.ts (production).

Local Dev Environment

From zero to a running Xuber HTMLUI on your machine

You need Node 20+, Angular CLI 17+, and VPN access to the Xuber API sandbox.

1

Clone the repo

git clone https://dxc-git/xuber-htmlui && cd xuber-htmlui

2

Install

nvm use 20 && npm install

3

Configure proxy

cp proxy.conf.example.json proxy.conf.json then set target to http://xuber-sandbox:8080

4

Start dev server

ng serve --proxy-config proxy.conf.json

5

Open in browser

Navigate to http://localhost:4200 and log in with sandbox credentials.

⚠️
Common issue: /api returns 404

Check proxy.conf.json target URL and confirm you are on VPN.

Concept 3

Debugging Xuber Angular Apps

Chrome DevTools and Angular DevTools — your two essential debug tools

Two tools cover 90% of Angular debugging in Xuber. Chrome DevTools for network and JS errors; Angular DevTools for component tree and change detection.

🌐 Network tab

Filter by /api. Check Payload and Response tabs for 400/500 errors. Use "Preserve log" across navigations.

> Console

Angular DI errors appear here. Use ng.getComponent(el) to inspect a live component. Source maps link to TypeScript.

🪠 Component tree

Inspect @Input values and signal state. Click a DOM element to find its component. Manually trigger change detection to test OnPush.

⏱ Profiler

Record a CD cycle to find slow components. Look for >5ms checks — candidates for OnPush on the Xuber policy grid.

Install Angular DevTools from the Chrome Web Store — search "Angular DevTools".

Working with the Xuber API

REST contracts, OpenAPI spec, and mocking for frontend development

The Xuber REST API uses OpenAPI (Swagger). Knowing the endpoint structure lets you build correct Angular services first time.

Policy API

/api/v2/policies

GET / list   GET /:id detail
POST / create   PATCH /:id endorse

Claims API

/api/v2/claims

GET / list   GET /:id detail
POST / open   POST /:id/payments pay

LMM API

/api/v2/lmm

GET /scm SCM records
GET /usm USM records
POST /cnr CNR submit

Auth API

/api/v2/auth

POST /login token
POST /refresh JWT refresh
DELETE /logout end session

In tests: Use HttpClientTestingModule — never call real endpoints in unit tests.

Branching, PRs & Code Review

The Xuber HTMLUI Git workflow from feature branch to merge

All changes go through a GitLab merge request with mandatory CI checks and two peer reviews.

1

Create branch

git checkout -b feat/XE-1234-policy-filter

2

Develop & test locally

ng test --watch && ng lint — all passing before push.

3

Push & open MR

git push origin feat/XE-1234-policy-filter

4

CI runs

Lint → build → tests → coverage. Must pass before review is assigned.

5

2 approvals required

Reviewers check types, logic, no console.log, no any, coverage maintained.

6

Squash merge to main

Triggers automatic deployment to QA environment.

Deploy Pipeline

From Git merge to Xuber Production via Azure Pipelines

Every merge to main kicks off the Azure DevOps pipeline automatically. Knowing each stage helps diagnose failures fast.

1 Build: ng build --configuration production
2 Unit Tests: ng test --no-watch --code-coverage — 80% gate
3 Deploy QA: qa.xuber-internal — smoke tests run automatically
4 UAT Sign-off: manual approval gate
5 Deploy PROD: blue-green to xuber.dxc.com
If your pipeline fails: Run ng build && ng test && ng lint locally to reproduce the issue before pushing a fix.

Concept 7

Xuber Coding Patterns

Team conventions that PR reviewers enforce — learn these before writing code

Deviating from these patterns causes PR rejections. Learn them before writing production code.

Services

Two service layers

PolicyApiService: raw HTTP only. PolicyFacadeService: orchestration. Components inject the Facade only.

Components

Smart vs Dumb

Smart: injects services, holds state. Dumb: @Input/@Output only, no services. Dumb components are easy to test.

Types

No 'any'

Every API call must be typed: http.get<Policy[]>(). The linter enforces no-explicit-any.

Performance

trackBy on *ngFor

All *ngFor loops must use trackBy to prevent full DOM re-renders on data refresh.

Subscriptions

async pipe preferred

Prefer {{ data$ | async }} over manual .subscribe() — handles unsubscription automatically.

Standalone

New components standalone

New components use standalone: true and import directly rather than declaring in a module.
