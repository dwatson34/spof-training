ITransactionPlugin Interface

Every transaction plugin implements this interface with a single method:

public interface ITransactionPlugin
{
    ProcessResultsCollection ProcessTransaction(
        IBusinessTransaction businessTransaction,
        TransactionInvocationPoint point,
        int pluginId,
        params object[] parameters);
}

Method Parameters Explained

Parameter Type Purpose
businessTransaction IBusinessTransaction The transaction instance. Access root component, context, etc.
point TransactionInvocationPoint Which lifecycle point the plugin is running at (PreCreate, PostComplete, etc.)
pluginId int Unique ID for this plugin instance (rarely used)
parameters object[] Additional parameters (internal use)

Return Value

ProcessResultsCollection — used to return errors/warnings. Return null if no errors.

Accessing Transaction Context

From within a plugin, access the transaction state via the Context property:

IBusinessTransaction businessTransaction = /* parameter */;

// Get the transaction context
TransactionContext context = businessTransaction.Context;

// Check if this is a display or edit transaction
bool isDisplayTransaction = context.IsDisplayTransaction;

// Get current user
SecurityUser currentUser = context.CurrentUser;

// Get root business component (what we're editing)
IBusinessComponent rootComponent = 
    businessTransaction.RootBusinessComponent;

Key Context Properties

  • IsDisplayTransaction — boolean. True if read-only, false if editing.
  • CurrentUser — SecurityUser. Who is running this transaction.
  • ProcessResults — Validation messages collection.
  • ComponentsToBeDeleted — Components marked for deletion.

Real Example from Xuber

if (!context.IsDisplayTransaction)
{
    // Only execute on edit transactions
    var claimHeader = businessTransaction.RootBusinessComponent 
        as ClaimHeader;
    if (claimHeader != null)
    {
        claimHeader.LastModifiedBy = context.CurrentUser.DisplayName;
        claimHeader.LastModifiedDate = DateTime.Now;
    }
}

IComponentPlugin Interface

Component plugins implement this interface with multiple methods:

public interface IComponentPlugin
{
    // Main processing method
    ProcessResultsCollection ProcessComponent(
        IBusinessComponent component,
        ProcessInvocationPoint point,
        int pluginId);

    // Field-specific processing (for FieldRetrieval point)
    ProcessResultsCollection FieldRetrieval(
        IBusinessComponent component,
        ProcessInvocationPoint point,
        ref Field field,
        int pluginId);
}

Method Usage

  • ProcessComponent — Called for most lifecycle points (Created, ComponentChange, Validation, etc.)
  • FieldRetrieval — Called only at FieldRetrieval point to modify field metadata (read-only, hidden, etc.)

AbstractComponentPlugin Base Class

Don't implement IComponentPlugin directly. Instead, inherit from AbstractComponentPlugin:

public class MyComponentPlugin : AbstractComponentPlugin
{
    public override ProcessResultsCollection ProcessComponent(
        IBusinessComponent component,
        ProcessInvocationPoint point,
        int pluginId)
    {
        // Your code here
        return null; // No errors
    }
}

Error and Warning Handling

Plugins communicate errors/warnings back via ProcessResultsCollection:

using Xiap.Framework.ProcessHandling;

ProcessResultsCollection results = new ProcessResultsCollection();

// Raise an error (stops transaction/prevents saving)
results.AddError("ERROR_CODE", 
    "Claim amount cannot exceed policy limit");

// Raise a warning (shown to user, doesn't stop)
results.AddWarning("WARNING_CODE", 
    "This claim is unusually large for this policy");

return results;

Using PluginHelper for Complex Messages

For messages with parameters and template text:

PluginHelper<ClaimHeader> pluginHelper = 
    new PluginHelper<ClaimHeader>(point, (ClaimHeader)component);

pluginHelper.AddError("ERROR_CLAIM_LOCKED",
    pluginHelper.Component.ClaimRef);

pluginHelper.AddWarning("WARNING_LARGE_AMOUNT",
    pluginHelper.Component.ClaimAmount.ToString());

return pluginHelper.ProcessResults;

Error vs Warning

  • Error — Prevents transaction completion. User cannot proceed.
  • Warning — Shown to user but transaction can continue.

Process Handlers — K2 BPM Integration

Process Handlers are a special type of Component Plugin that orchestrate K2 workflows:

public class EventProcessHandler : IProcessHandler
{
    private readonly IProcessHandlerHelper _processHandlerHelper;

    public EventProcessHandler(IProcessHandlerHelper helper)
    {
        _processHandlerHelper = helper;
    }

    public ProcessResultsCollection ProcessHandler(
        IBusinessComponent component,
        ProcessInvocationPoint point,
        int pluginId,
        ProcessParameters processParameters)
    {
        // Use ProcessHandlerHelper to start a K2 process
        var processHelper = ObjectFactory.Resolve<IProcessHandlerHelper>();
        
        processHelper.InstantiateProcess(
            "EventProcess",  // K2 process name
            "Event-001",     // folio
            new Dictionary<string,object>(),  // properties
            new List<IBusinessComponent>());   // linked components
        
        return null;
    }
}

Key Points

  • Process Handlers run at the Virtual invocation point
  • They start K2 BPM workflows with business components as input
  • Use IProcessHandlerHelper.InstantiateProcess to start workflows
  • Configured via ProcessParameters (alias, etc.)

Plugin Predicates and Decision Tables

Control when a plugin executes using Predicates and Decision Tables:

Configuration-Based Predicates

<BPProcess businessProcess="Xiap.UW.BusinessTransaction.AmendQuote"
 point="PostComplete"
 sequence="60"
 type="Xiap.Framework.Common.EventProcessHandlerPlugin,..."
 predicateType="UwProductCode" predicate="PROD01,PROD02" />

Decision Table Predicates

Use a database decision table to determine if plugin runs:

<Component component="Xiap.Claims.BusinessComponent.ClaimHeader"
 point="Created"
 sequence="10"
 type="Xiap.Claims.BusinessLogic.ClaimHeaderPlugin,..."
 predicateType="UwDecisionTable" predicate="AssumedRIBase" />

The decision table is looked up in Design Studio. Based on Product Code, the predicate group determines if the plugin runs.

Predicate Types

  • ClaimProductCode — Run only for specific claims product codes
  • UWProductCode — Run only for specific underwriting product codes
  • ClaimsDecisionTable — Run based on claims decision table lookup
  • UwDecisionTable — Run based on UW decision table lookup

Real Example — A Complete Plugin

A realistic plugin that validates claim amounts against policy limits:

public class ClaimAmountValidationPlugin : AbstractComponentPlugin
{
    public override ProcessResultsCollection ProcessComponent(
        IBusinessComponent component,
        ProcessInvocationPoint point,
        int pluginId)
    {
        // Only validate on the Validation point
        if (point != ProcessInvocationPoint.Validation)
            return null;

        var claimDetail = component as ClaimDetail;
        if (claimDetail == null) return null;

        PluginHelper<ClaimDetail> helper = 
            new PluginHelper<ClaimDetail>(point, claimDetail);

        // Get the parent claim header
        var claimHeader = claimDetail.ClaimHeader;
        
        // Validate amount doesn't exceed limit
        if (claimDetail.ClaimAmount > claimHeader.CoverageLimit)
        {
            helper.AddError("CLAIM_EXCEEDS_LIMIT",
                $"Claim amount {claimDetail.ClaimAmount} " +
                $"exceeds policy limit {claimHeader.CoverageLimit}");
        }

        return helper.ProcessResults;
    }
}

This plugin runs at the Validation point and prevents saving if amount exceeds limit.

Scenario Challenge 1

Challenge: Audit Trail Plugin

Requirement: Create a transaction plugin that logs every transaction completion with the user who made the change.

Questions:

  1. Which transaction lifecycle point should you run at? (PostComplete or PostRollback?)
  2. How do you access the current user from within the plugin?
  3. How would you log the transaction details (ID, user, timestamp)?

Answer: PostComplete point (plugins can't modify at PostRollback, but logging still works). Access user via businessTransaction.Context.CurrentUser. Log to database or file with transaction ID, user name, and DateTime.Now.
