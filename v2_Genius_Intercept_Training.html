Concept 1

Genius Intercept Product

What Intercept is and why it is critical to Xuber operations

Genius Intercept is the integration and messaging middleware between Genius on iSeries and external systems including Xuber. It translates, routes and delivers business events. If Intercept stops, Genius continues locally but nothing is visible in Xuber.

What Intercept handles

Policy events

Policy lifecycle

Every Genius policy action - new business, endorsement, renewal, cancellation - generates a message to Xuber and downstream systems.

Claim events

Claim notifications

New claims, reserve changes, payments and closures are published to claims tracking systems and regulatory reporting.

Financial events

Accounting messages

Premium receipts, payment disbursements and bordereaux batches are routed to the insurer's finance system.

External feeds

Inbound data

Credit scores, DVLA vehicle data and fraud check results come inbound through Intercept into Genius at quote stage.

Intercept in the stack

External systems - finance, DVLA, fraud
Genius Intercept - message broker
IBM MQ - message queues
Genius on iSeries - event source
Xuber API - event consumer
If Intercept stops: Genius continues. Policies and claims are created in Genius but are not visible in Xuber until messages are processed. The backlog queues and processes when Intercept restarts.

Concept 2

Intercept Messaging Architecture

Topics, queues, routing rules and message flow

Intercept uses a publish-subscribe model. Genius publishes events to topics. Intercept routes them to subscriber queues based on routing rules. Consumers read from their subscribed queues.

Key components

Topics

Event categories

POLICY.EVENTS, CLAIM.EVENTS, FINANCIAL.EVENTS, PARTY.EVENTS. Each Genius action publishes to the appropriate topic.

Queues

Subscriber delivery

Each consumer has a named queue. Xuber API reads from XUBER.POLICY.IN and XUBER.CLAIM.IN.

Routing Rules

Message filtering

XPath rules determine which messages from a topic go to which queues. Only Active policy events route to the bordereaux system.

Dead Letter Queue

Failed messages

Messages that cannot be processed go to the DLQ. All DLQ messages require investigation and replay or discard.

Message flow exampleFlow
1. User binds policy in Genius
   |
2. Genius posts to iSeries data queue
   GENIUSPRD.POLICY.OUT
   |
3. Intercept adapter reads queue,
   transforms to XML message
   |
4. Publishes to POLICY.EVENTS
   topic (type=BOUND)
   |
5. Routing rule: BOUND routes to
   XUBER.POLICY.IN
   BORDEREAUX.POLICY.IN
   |
6. Xuber API reads XUBER.POLICY.IN,
   updates XuberCore database
   |
7. Policy visible in Xuber HTMLUI
Latency: Under normal load steps 1 through 7 complete in under 2 seconds. Growing queue depth increases this. Users notice delays over 30 seconds.

Concept 3

Queue Monitoring and Daily Health Check

Checking queue depths, thresholds and the morning health check procedure

Queues are healthy when their depth is near zero - messages arrive and are consumed quickly. A growing queue means either the consumer has stopped or messages are arriving faster than they can be processed.

Queue depth thresholds

0 to 10 messages

Normal

Messages arriving and consumed in near-real-time. No action needed.

10 to 100 messages

Monitor closely

Slightly elevated. Check if a consumer has slowed. Monitor for 15 minutes. If not reducing, investigate.

Over 100 messages

Investigate immediately

Consumer may have stopped. Find and fix the consumer issue. Impact: delayed Xuber updates visible to users.

DLQ over 0

Action required

All DLQ messages must be reviewed. Replay valid ones. Discard malformed ones. Log every DLQ message reviewed.

Morning health check - 5 minutes

1

Open Intercept console

http://intercept-server:8080/IntMgmt - all topics and queues should show green with near-zero depths.

2

Check DLQ depth

DLQ must be zero. If not, open each message, read the error reason, and resolve per the troubleshooting guide.

3

Review overnight message counts

Dashboard shows messages processed overnight. Renewal batch typically processes 500 messages overnight. Significantly lower count means the Genius scheduler may not have run.

4

Log the result

Record in the ops log: time, result (green or issues), any DLQ messages resolved, and your name. This is the SLA reporting evidence trail.
