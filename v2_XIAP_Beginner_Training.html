What is XIAP?

XIAP is the core application framework that underpins Xuber Enterprise. It is not simply an API layer or scheduler.

XIAP Provides

  • Plugin Execution Framework — executes custom C# plugins at defined lifecycle points
  • Component Lifecycle Management — creates, modifies, validates, and deletes business components
  • Transaction Management — controls changes to business components atomically
  • Configuration Management — loads and manages Processes.config and Unity.config
  • Scheduler Services — background job execution (K2 BPM integration)
  • Global Search Services — indexed search across Xuber data
  • Integration Processing — message handling and API integration

Key Insight

Xuber business functions appear to run on top of XIAP. In reality, XIAP controls the execution:

  • Loads configuration
  • Manages component lifecycles
  • Invokes plugins at the right time
  • Handles transactions and locking

Plugin Architecture

XIAP provides two main types of plugins that developers write:

1. Transaction Plugins

Implement ITransactionPlugin interface. Execute during the lifecycle of a business transaction.

  • Called at specific transaction points: PreCreate, PostCreate, PreComplete, PostComplete, PreRollback, PostRollback
  • Can make changes to business component structure (at PreComplete point)
  • Can raise errors that prevent transaction completion
  • Typical use: validate business rules, trigger external processes, audit logging

2. Component Plugins

Implement IComponentPlugin interface. Execute during the lifecycle of a business component.

  • Called at lifecycle points: PreCreateValidation, Created, ComponentChange, Virtual, Validation, ValidateDelete, etc.
  • Can add validation rules, set defaults, compute values
  • Can raise errors that prevent component creation, modification, or deletion
  • Typical use: field validation, default values, computed fields, audit trails
Process Handlers: A special type of Component Plugin that orchestrates K2 BPM workflow. Invoked via the Virtual point.

Transaction Lifecycle Points

Every business transaction flows through these lifecycle points. Plugins are configured to run at specific points:

Point Description Can Modify Components?
PreCreate Before transaction starts. Errors abort the transaction. No
PostCreate After transaction starts. Errors shown to user. No
PreComplete Before saving changes. Plugins can modify components. Must be careful with invalid data. Yes
PostComplete After saving changes. Cannot modify components. Errors roll back changes. No
PreRollback Before rolling back. Cleanup operations. No
PostRollback After rollback. All changes reverted. No

Plugin Execution Order

Multiple plugins can run at the same point. They execute in sequence order (configured in Processes.config).

Component Lifecycle Points

Business components follow their own lifecycle independent of transactions:

Point Purpose
PreCreateValidation Validation before component creation. Errors prevent creation.
Created Component just created. Perform defaulting (set initial values).
ComponentChange Component was modified. React to field changes.
PreValidationDefaulting Default values before validation runs.
Validation Validate component. Errors prevent saving.
ValidateDelete Validate component for deletion. Errors prevent deletion.
FieldRetrieval Modify field metadata before display.
Virtual On-demand invocation (not automatic). Process Handlers run here.

How Plugins Are Configured

Plugins require two things: Code and Configuration.

Processes.config — Registering Plugins

Transaction plugin example:

<BPProcess businessProcess="Xiap.UW.BusinessTransaction.AmendQuote"
 point="PostComplete"
 sequence="60"
 type="Xiap.Framework.Common.EventProcessHandlerPlugin,Xiap.Framework.Common" />

Component plugin example:

<Component component="Xiap.Claims.BusinessComponent.ClaimHeader"
 point="ComponentChange"
 sequence="10"
 type="Xiap.Claims.BusinessLogic.ClaimHeaderPlugin, Xiap.Claims.BusinessLogic" />

Key Attributes

  • businessProcess or component — The .NET type the plugin handles
  • point — The lifecycle point where plugin executes
  • sequence — Order of execution (lower runs first). Custom plugins should use >100
  • type — Assembly-qualified .NET type of the plugin class
Important: Sequences 1-99 are reserved for Xuber core. Use 100+ for custom plugins.

Your First Plugin — The Basics

A minimal transaction plugin that logs when a transaction completes:

using Xiap.Framework.ProcessHandling;
using Xiap.Framework.TransactionHandling;

public class MyFirstPlugin : ITransactionPlugin
{
    public ProcessResultsCollection ProcessTransaction(
        IBusinessTransaction businessTransaction,
        TransactionInvocationPoint point,
        int pluginId,
        params object[] parameters)
    {
        if (point == TransactionInvocationPoint.PostComplete)
        {
            // Log that transaction completed
            System.Diagnostics.Debug.WriteLine(
                "Transaction completed successfully!");
        }
        
        return null; // No errors
    }
}

To Deploy This Plugin

  1. Compile to a .NET 4.0 Class Library assembly
  2. Place .dll in \bin folder of Xuber web application
  3. Add entry to Processes.config pointing to the plugin class
  4. Restart Xuber web application
  5. Plugin will now execute at the configured point

Key Takeaways — Beginner Level

What You Now Understand

  • XIAP is the core framework that controls Xuber's execution model
  • Plugins are C# classes that extend XIAP's behavior at specific lifecycle points
  • Transaction plugins run during transaction lifecycle (PreCreate → PostRollback)
  • Component plugins run during component lifecycle (PreCreateValidation → Virtual)
  • Configuration (Processes.config) registers plugins and defines when they run
  • Sequence determines execution order when multiple plugins run at the same point
