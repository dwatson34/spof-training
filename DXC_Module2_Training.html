Signals & Component State

Angular 17+ reactive primitives for fine-grained, automatic state management

Signals are Angular's modern reactive primitive. A signal holds a value; any template or computed expression that reads it re-runs automatically when it changes — no manual subscriptions.

The three signal APIs

signal()

Writable signal

Creates a reactive value. Read it by calling it: count(). Update with count.set(5) or count.update(v => v+1).

computed()

Derived signal

Read-only. Angular recalculates it only when its dependencies change — like a memoised getter.

effect()

Side effect

Runs a side effect whenever signals it reads change. Useful for logging or syncing to localStorage.

OnPush

Change detection

Pair signals with ChangeDetectionStrategy.OnPush for maximum performance on large Xuber grids.

policy-list.component.tsTypeScript
policies = signal<Policy[]>([]);

activeCount = computed(() =>
  this.policies()
    .filter(p => p.status === 'Active')
    .length
);

constructor() {
  effect(() => {
    console.log(
      `Active: ${this.activeCount()}`
    );
  });
}
vs Observables: Signals are synchronous and simpler for local component state. Use Observables (HttpClient) for async API calls, and signals for derived UI state.

Reactive Forms

Type-safe, testable forms built entirely in TypeScript using FormBuilder

Reactive Forms define the form structure in the component class. Unlike Template-Driven forms, all validation and state live in TypeScript — making them easier to test and dynamically modify.

Form building blocks

FormGroup

Groups controls

Represents the whole form or a section. Tracks validity of all contained controls as a unit.

FormControl

Single input

Represents one field. Tracks value, validity, touched, and dirty state.

FormArray

Dynamic list

A list of controls — ideal for repeating sections like multiple policy endorsements.

Validators

Validation rules

Built-in: required, minLength, email, min. Or write custom validators.

claim-form.component.tsTypeScript
claimForm = this.fb.group({
  claimRef: ['', [
    Validators.required,
    Validators.minLength(6)
  ]],
  amount: [0, [
    Validators.required,
    Validators.min(0)
  ]],
  description: ['']
});

// Template:
// <form [formGroup]="claimForm">
// <input formControlName="claimRef">
Show validation errors: Use claimForm.get('claimRef').hasError('required') in the template with *ngIf to show inline error messages.

Lazy Loading

Load feature modules on demand to keep the initial bundle small and fast

By default Angular bundles everything together. Lazy loading splits the app into separate JavaScript chunks — each feature module is only downloaded when the user navigates to that route for the first time.

Without lazy loading — slow first load
AppModule
PolicyModule — loaded upfront
ClaimsModule — loaded upfront
LmmModule — loaded upfront
With lazy loading — fast first load
AppModule (tiny)
PolicyModule — downloaded on /policies
ClaimsModule — downloaded on /claims
LmmModule — downloaded on /lmm
app-routing.module.tsTypeScript
{
  path: 'claims',
  loadChildren: () => import(
    './claims/claims.module'
  ).then(m => m.ClaimsModule)
  // Angular downloads claims chunk only when
  // the user navigates to /claims
}
Rule of thumb: Every Xuber feature module (Policy, Claims, LMM) should be lazy-loaded. Only truly shared code (SharedModule, CoreModule) should be in the initial bundle.

RxJS Operators in Practice

Five operators that appear constantly in the Xuber Angular codebase

Beyond the basics, these operators solve specific real-world problems when building responsive, robust Xuber UI features. Each removes a class of bug.

debounceTime(300)Use case: Search-as-you-type — wait 300ms after last keystroke before calling the API. Prevents dozens of unnecessary requests.
input$.pipe(debounceTime(300), switchMap(q => api.search(q)))
switchMap()Use case: Cancel the previous HTTP call when a new one starts. Prevents stale responses from earlier queries overwriting newer ones.
route.params.pipe(switchMap(p => policyService.get(p.id)))
combineLatest()Use case: Combine two streams (e.g. active filters + policy data) and emit whenever either changes — perfect for Xuber filter bars.
combineLatest([filters$, policies$]).pipe(map(([f,p]) => applyFilter(f,p)))
catchError()Use case: Intercept errors, log them, and return a safe fallback Observable so the UI doesn't crash.
http.get('/api/policies').pipe(catchError(e => of([])))
takeUntilDestroyed()Use case: Auto-unsubscribe when the component is destroyed. Replaces manual ngOnDestroy cleanup entirely.
this.svc.data$.pipe(takeUntilDestroyed()).subscribe(...)

HTTP Error Handling

Interceptors, catchError, retry strategies, and user-facing feedback

Unhandled HTTP errors cause blank screens in the Xuber UI. Angular provides two layers of protection: per-request catchError in services, and global HTTP Interceptors that catch everything.

The two-layer strategy

HTTP Request leaves Angular
HTTP Interceptor
Add auth headers, log, retry, handle 401/500
Service catchError()
Per-call fallback and error mapping
Component template
Show loading / error state with *ngIf
User sees toast / inline message
error-interceptor.tsTypeScript
intercept(req, next) {
  return next.handle(req).pipe(
    retry({ count: 2, delay: 1000 }),
    catchError(err => {
      if (err.status === 401)
        this.auth.logout();
      this.toast.show(
        err.message
      );
      return throwError(
        () => err
      );
    })
  );
}
Register the interceptor in AppModule providers:
{ provide: HTTP_INTERCEPTORS, useClass: ErrorInterceptor, multi: true }
