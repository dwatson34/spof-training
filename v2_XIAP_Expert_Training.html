Advanced Plugin Predicates

Control plugin execution with sophisticated predicate logic:

Predicate Types (Deep Dive)

Type Usage
ClaimProductCode Run for specific claims product codes. Multiple codes separated by comma.
UWProductCode Run for specific underwriting product codes.
GenericDataItemTypeCode Run for specific generic data type codes.
ClaimsDecisionTable Decision table lookup determines if plugin runs. Matched against claims product code.
UwDecisionTable Decision table lookup for underwriting product code.

Real Configuration Example

<Component component="Xiap.Claims.BusinessComponent.ClaimDetail"
 point="Validation"
 sequence="150"
 type="MyPlugins.ClaimDetailValidationPlugin,MyPlugins"
 predicateType="ClaimsDecisionTable" 
 predicate="X-CLAIM-VALIDATION" />

This plugin only runs for claims whose product code matches entries in the decision table "X-CLAIM-VALIDATION".

Decision Table Execution Control

Plugins can check predicates at runtime using the CanExecute method:

public class MyDecisionTablePlugin : AbstractComponentPlugin
{
    public override ProcessResultsCollection ProcessComponent(
        IBusinessComponent component,
        ProcessInvocationPoint point,
        int pluginId)
    {
        if (point != ProcessInvocationPoint.Validation)
            return null;

        var claimHeader = component as ClaimHeader;
        
        // Manually check if we should run
        bool canRun = CanExecute(
            claimHeader,
            point,
            "MyPluginName",
            new string[] { "DECISION_TABLE_VALUE1", "DECISION_TABLE_VALUE2" });
        
        if (!canRun) return null;
        
        // Plugin logic here
        return null;
    }
}

Decision Table Reference

Decision tables are defined in Design Studio with rows like:

  • Product Code — The product code to match
  • Plugin Group — Group name (e.g., "MyPluginGroup")
  • Plugin — Specific plugin name
  • Result — TRUE/FALSE whether to run

Accessing Business Objects & Services

Plugins often need to interact with business services and objects:

Resolving Objects via ObjectFactory

// Get security service
var securityService = ObjectFactory.Resolve<ISecurityService>();
var user = securityService.FindUsersByNameID(nameId).FirstOrDefault();

// Get currency service
var currencyService = ObjectFactory.Resolve<ICurrencyService>();
decimal convertedAmount = currencyService.ConvertCurrency(
    amount, "GBP", "USD", DateTime.Now);

// Get decision table helper
var dtHelper = ObjectFactory.Resolve<IDecisionTableHelper>();
var decisionTableComponent = dtHelper.Call(
    "TABLE_CODE", DateTime.Now, conditions);

Accessing Component Relationships

var claimHeader = (ClaimHeader)component;

// Get all related claim details
var claimDetails = claimHeader.ClaimDetail; // ICollection

// Access parent component
var parentComponent = claimHeader.ParentComponent;

// Check if component is new (vs. existing)
bool isNew = claimHeader.IsNew;

Working with Static Values & Metadata

Access static values, system values, and field metadata:

Static Values (Enums)

// Static values are accessed via enums
var coverageCategory = (StaticValues.CoverageCategory)
    coverageCode.CoverageCategory.GetValueOrDefault((short)0);

// Use GetValueOrDefault to avoid null exceptions
var riskType = (StaticValues.RiskType)
    claimDetail.RiskTypeCode.GetValueOrDefault(
        (short)StaticValues.RiskType.Standard);

System Values (Database Lookups)

var systemValueQuery = ObjectFactory.Resolve<ISystemValueSetQuery>();
var values = systemValueQuery.Query<HeaderStatusData>()
    .Where(x => x.IsActive == true)
    .ToList();

Field Metadata Access

// Get Field object for a property
Field claimTitleField = claimHeader.ClaimTitleField;

// Check if field is mandatory
bool isMandatory = claimTitleField.IsMandatory;

// Check if field is read-only
bool isReadOnly = claimTitleField.IsReadOnly;

Important Pattern

Always use GetValueOrDefault() when casting nullable static values to avoid null reference exceptions.

Advanced Error Handling

Complex error scenarios and message handling patterns:

Conditional Error Handling

public override ProcessResultsCollection ProcessComponent(
    IBusinessComponent component,
    ProcessInvocationPoint point,
    int pluginId)
{
    var results = new ProcessResultsCollection();
    var claimDetail = component as ClaimDetail;
    
    // Only check errors on edit transactions
    var transContext = claimDetail.Context;
    if (transContext.IsDisplayTransaction)
        return null; // No validation on read-only
    
    // Multi-level validation
    if (claimDetail.ClaimAmount < 0)
    {
        results.AddError("NEGATIVE_AMOUNT", 
            "Claim amount cannot be negative");
    }
    else if (claimDetail.ClaimAmount > 1000000)
    {
        results.AddWarning("VERY_LARGE_CLAIM",
            "Claim amount exceeds £1,000,000");
    }
    
    return results.Count > 0 ? results : null;
}

Message Configuration

Messages must be registered in Config.Message table with:

  • MessageAlias — Unique identifier (e.g., "CLAIM_EXCEEDS_LIMIT")
  • MessageType — 4 = Customer (for custom plugins)
  • MessageCategory — Category code (1=Underwriting, etc.)

Message text is configured in Config.MessageTemplate with language support and replaceable parameters.

Performance & Best Practices

Production-grade plugin patterns and performance considerations:

Performance Tips

  • Lazy Load Services — Only resolve services you actually use
  • Batch Operations — Don't make separate service calls in loops
  • Cache Static Data — Resolve ISystemValueSetQuery once, not per component
  • Avoid Unnecessary Checks — Early returns on conditions that skip processing
  • Minimize Database Calls — Use existing component data before querying

Anti-Patterns to Avoid

// DON'T DO THIS - Resolves service in loop
foreach (var detail in claimHeader.ClaimDetail)
{
    var currencyService = ObjectFactory.Resolve<ICurrencyService>();
    // ...expensive operation
}

// DO THIS - Resolve once, reuse
var currencyService = ObjectFactory.Resolve<ICurrencyService>();
foreach (var detail in claimHeader.ClaimDetail)
{
    // ...use service here
}

Error Handling Best Practice

Plugins should never throw exceptions. Always catch exceptions and return errors via ProcessResultsCollection.

Expert Scenario Challenge 1

Challenge: Multi-Condition Validation Plugin

Requirement: Create a component plugin that validates a claim detail based on multiple conditions:

  1. If claim amount > coverage limit, raise ERROR
  2. If claim amount > £50,000 AND product code = "SPECIAL", convert currency from EUR to GBP
  3. If risk type = "Marine", validate that deductible is set
  4. Only run this validation for specific product codes (use predicates)

Problem: How would you structure this plugin to handle all 4 conditions efficiently?

Approach: Use predicate to filter at config level (condition 4). In code, check point first (early return if not Validation). Resolve services once at top. Check conditions in order (cheapest first). Use GetValueOrDefault() for enums. Return null if no errors for performance.
