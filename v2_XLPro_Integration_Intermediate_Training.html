XLPro Integration — Intermediate

Learn the detailed installation steps, configuration parameters, and deployment procedures for XLPro Integration in production environments.

Installation Steps

Step 1: Download the latest XLPro package from your artifact repository
Step 2: Verify Java 11+ is installed, database connectivity works, and required ports are open
Step 3: Extract to /opt/xlpro with proper permissions: unzip xlpro-[version].zip
Step 4: Configure xlpro.properties with your environment details (broker, database, ports)
Step 5: Run startup.sh and monitor logs: tail -f xlpro-startup.log
Quick Check
After extraction, startup.sh fails with "Port 5672 already in use". What's the issue?
✅ Correct! The right answer is: RabbitMQ or another service is using that port - change xlpro.properties or stop the other service

Configuration Deep Dive

Master the critical configuration parameters that control performance, reliability, and integration behavior.

Critical Configuration Parameters

Message Broker Settings ▼

RabbitMQ Connection Configuration:

  • broker.host: Hostname or IP of RabbitMQ server
  • broker.port: AMQP port (default 5672, 5671 for SSL)
  • broker.username: Service account for XLPro (never use 'guest' in production)
  • broker.password: Always use environment variable ${BROKER_PASSWORD}, never hardcode
  • broker.vhost: Virtual host for isolation (e.g., /xlpro-prod)
Performance Tuning Parameters ▼

Key Performance Settings:

  • db.connection.pool.size: Max concurrent database connections (default 20, increase for high load)
  • message.batch.size: Messages to batch before commit (default 100, higher = better throughput but more memory)
  • performance.thread.pool: Worker threads for message processing (typically 2x CPU cores)
  • timeout.message.process.ms: Max processing time per message (default 30000ms)
Quick Check
Message processing is slow with low CPU usage. What configuration do you check first?
✅ Correct! The right answer is: db.connection.pool.size - likely too low for current load

Routing & Transformation Rules

Configure how messages are routed to subscribers and transformed for different external systems.

Creating Routing Rules

Routing rules determine which messages go to which queues based on message type, source, and custom filters.

Rule Syntax & Examples ▼

Basic Structure:

rule: "PolicyCreated" {
  source: "xuber.policy",
  topic: "/policy/created",
  targetQueues: ["reinsurance-inbound", "accounting-inbound"],
  filter: "status == 'ACTIVE'",
  priority: 10
}

Filter Examples:

  • status == 'ACTIVE' AND amount > 1000
  • product IN ('Auto', 'Home') AND region == 'EMEA'
  • source matches 'xuber.*' AND NOT internal
Quick Check
You create a routing rule for policy events but no messages appear in the target queue. First diagnostic step?
✅ Correct! The right answer is: Check if the filter condition matches incoming messages - test with actual message samples

Monitoring & Health Checks

Monitor XLPro Integration health, identify bottlenecks, and respond to failures in production.

Key Metrics to Monitor

Queue Depth: Messages waiting in queue. Alert if > 100 (consumer may be down)
Message Latency: Time from publish to delivery. Alert if > 5 seconds
Dead Letter Queue Depth: Messages that failed. Alert if > 10 (investigation needed)
Connection Pool Usage: Active connections. Alert if > 80% of pool.size
Quick Check
Morning health check shows 500 messages in the DLQ. What does this indicate?
✅ Correct! The right answer is: A systemic problem occurred - multiple messages failed. Investigate root cause immediately.

Deployment Best Practices

Deploy XLPro Integration safely to production with zero downtime and full rollback capability.

Rolling Deployment Process

Step-by-Step Deployment ▼
  1. Pre-deployment: Run full test suite, verify database migrations, backup current version
  2. Drain traffic: Stop sending messages to first instance (load balancer)
  3. Deploy: Update code, restart service on first instance
  4. Verify: Check logs for errors, monitor metrics for 5 minutes
  5. Health check: Send test messages, verify they process correctly
  6. Resume traffic: Re-enable first instance in load balancer
  7. Repeat: For each remaining instance
  8. Monitor: Watch for 30 minutes for any issues
Quick Check
After deploying to production, you notice message errors increasing. What's the best action?
✅ Correct! The right answer is: Immediately rollback by redeploying previous version, investigate root cause separately

Troubleshooting Guide

Diagnose and resolve common XLPro Integration issues in production.

Common Issues & Solutions

Issue: Messages in Dead Letter Queue ▼

Root causes:

  • Transformation rule mismatch (message format unexpected)
  • Routing rule filter too restrictive (message gets rejected)
  • External system credentials expired or permissions revoked
  • Target database or API endpoint down

Solution steps:

  1. Read the DLQ message content and error details
  2. Verify routing and transformation rules match the message
  3. Test external system connectivity
  4. Fix the issue and manually replay the message
Quick Check
Troubleshooting a transformation failure. First diagnostic step?
✅ Correct! The right answer is: Read the DLQ message and compare format to transformation rules
