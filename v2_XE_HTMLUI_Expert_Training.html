Adding a New Service Method

Click ▶ to step through the complete safe process. Every step is required.

Adding a new API call to the Xuber HTMLUI requires following the established convention exactly. Deviating from the pattern causes inconsistency and subtle bugs. This is the complete 7-step process from reading the .NET API contract to verifying in the Network tab.

The complete process — click ▶ to step through

Click to step through
1

Read the .NET API controller

Find the controller method in Xuber.Web.Api. Note the exact route string (case matters), the parameter names and types, and the return type. The .NET route string IS your private static ApiPath value.

2

Choose the right service file

Claims operations go in xuClaims.service.ts, underwriting in xuUnderwriting.service.ts. Never create a new service file unless the domain genuinely does not exist.

3

Declare the private static endpoint constant

Add private static myEndpointApiPath = 'api/domain/MyEndpoint'; immediately above the method. Must exactly match the .NET route — case sensitive.

4

Write the method with the correct pattern

Build the params object. Param names in the object must match .NET parameter names exactly — check spelling and case. Use ? suffix for optional params. Use .post() if any param is an array.

5

Add .then() with xuLoggerService.debugResponse()

.then(response => { this.xuLoggerService.debugResponse(url); return response; }) is mandatory. PRs missing this should be rejected.

6

Inject and call in the component

The service is already injected in most components via the constructor. Call the method on a user event or in ngOnInit. Handle both .then() (success) and .catch(retVal => { retVal.errorMsg }) (failure).

7

Verify in the Network tab

Trigger the call. In Network tab filtered by api/, verify: correct URL with /XuberHTMLApi/ prefix, correct Query String Parameters, Status 200, correct Response shape.

Complete new method — correct Xuber patternTypeScript
private static getClaimReopenEligibilityApiPath =
  'api/claims/GetClaimReopenEligibility';

getClaimReopenEligibility(
  claimReference: string,
  claimStage: number,
  reopenReasonCode?: string
) {
  var params = {
    claimReference: claimReference,
    claimStage: claimStage,
    reopenReasonCode: reopenReasonCode
  };
  let url = XuClaimsService
    .getClaimReopenEligibilityApiPath;
  return this.xuWebApiManager
    .get(url, params)
    .then(response => {
      this.xuLoggerService
        .debugResponse(url);
      return response;
    });
}

Common mistakes to avoid

The most frequent cause of 400 errors on new methods is a mismatch between Angular params object keys and .NET parameter names. Example: Angular sends claimRef but .NET expects claimReference. Always copy param names directly from the .NET controller method signature.
Arrays sent via $.param() as query strings may be malformed. Use xuWebApiManager.post() whenever any param is an array. This is exactly why changeHandler uses POST. Only the .get() vs .post() call changes — everything else is identical.
This is a mandatory Xuber convention. Its absence signals the method does not follow the established pattern. It provides the console call trail all debugging relies on. Reject and require it.

Feature Module (e.g. claims.module.ts)

Each feature has its own Angular module. It imports SharedModule (providing common components, directives and pipes), declares all feature components, and sets up feature-specific routing. Common services like XuClaimsService are provided at root level — feature modules just inject them.

Feature component — typical patternTypeScript
@Component({
  selector: 'xu-close-claim-dialog',
  templateUrl: './xuCloseClaimDialog.html'
})
export class XuCloseClaimDialogComponent {
  constructor(
    private claimsService: XuClaimsService
  ) {}

  closeClaim(claimRef: string) {
    this.claimsService
      .startAmendClaimsTransaction(
        claimRef, this.claimStage, false
      )
      .then(response => {
        // handle success
      })
      .catch(retVal => {
        // retVal.errorMsg
        // retVal.errorObject
      });
  }
}
The xu prefix convention: All Xuber components use the xu prefix. Class: XuComponentNameComponent. Selector: xu-component-name. Any new component must follow this. It is enforced across all 8 feature areas.
XuClaimsService, XuUnderwritingService and all other common services are provided in app.module.ts or CoreModule — making them singletons shared across all features. Feature modules do not provide them. Components just declare them in the constructor.
TypeScript interfaces for API responses live in common/interfaces/ and common/dataTypes/. When a service returns data, components can cast to these interfaces. Domain-specific types may also be in common/models/ within each service’s subfolder.

Lazy Loading & Routing

Click each route to understand when it loads and how to diagnose routing failures.

All 8 feature modules are lazy-loaded. The JavaScript bundle for each feature only downloads when the user first navigates there. Understanding this is essential for diagnosing load failures and ChunkLoadErrors.

app.routing.module.ts — complete real routesTypeScript
const appRoutes: Routes = [
  { path: '', redirectTo: 'home',
    pathMatch: 'full' },
  { path: 'error',
    component: XuErrorComponent },
  { path: 'home',
    loadChildren: () => import(
      './feature/home/home.module')
      .then(m => m.HomeModule) },
  { path: 'task',
    loadChildren: () => import(
      './feature/tasks/tasks.module') },
  { path: 'claims',
    loadChildren: () => import(
      './feature/claims/claims.module') },
  { path: 'underwriting',
    loadChildren: () => import(
      './feature/underwriting/...') },
  { path: 'accounts',
    loadChildren: () => import(
      './feature/accounts/...') },
  { path: 'xlpro',
    loadChildren: () => import(
      './feature/xlpro/xlpro.module') },
  { path: 'lmm',
    loadChildren: () => import(
      './feature/lmm/lmm.module') },
];
RouterModule.forRoot(appRoutes, {
  enableTracing: !environment.production
})
Route Tracing

enableTracing: !environment.production

Active in dev and test. Logs every Angular router event to the console: NavigationStart, RouteConfigLoadStart, RouteConfigLoadEnd, NavigationEnd. Essential for diagnosing routing failures and lazy load timing.

Error Route

XuErrorComponent

The error route is a standard component (not lazy-loaded). It renders immediately. Navigation failures and authentication errors redirect here. Check the URL params on this screen — they often contain the error code.

ChunkLoadError

Blank screen + Console error

A ChunkLoadError with 404 in the Network tab means the lazy-loaded bundle was not deployed. Check build artefacts and deployment logs. Not a code bug — a build/deployment issue.

First Navigation

Visible delay is normal

The first navigation to a feature causes a visible pause while the chunk downloads. All subsequent visits use the cached bundle. If users report slowness only on first visit to a module, this is expected Angular lazy-load behaviour.

Advanced Debugging

Click ▶ to step through the Expert multi-layer diagnosis approach.

Expert debugging means diagnosing failures spanning multiple layers — component through service through XuWebApiManager to the .NET API. This systematic approach handles the hardest failure types.

Multi-layer diagnosis — click ▶

Click to step through
1

Establish the symptom layer

Is the API call being made at all? If yes, check the response. If no, the problem is in the component — the service method was never called, or was called with null values.

2

Read the Console xuLoggerService trail

Filter Console by debugResponse. This shows all API calls that completed. Compare the sequence to what should have happened. A missing entry tells you exactly where the chain broke.

3

Decode an invokeAction call

Click api/claims/invokeAction or api/underwriting/invokeAction in Network tab. Headers → Query String Parameters. The actionName param is the real operation. The args param shows what data was sent.

4

Cross-reference the .NET source

Take the API path. Find the matching controller action in Xuber.Web.Api. Compare parameter names. A 400 almost always means a param name mismatch between the Angular params object and the .NET action signature.

5

Check the full retVal error chain

In the component .catch(), log both retVal.errorMsg and JSON.stringify(retVal.errorObject). The errorObject may contain field-level validation errors not surfaced in errorMsg.

6

Rule out CORS/proxy issues last

CORS errors appear as network failures with no HTTP status. Only occur locally without --proxy-config proxy.conf.json. If you see red Network entries with no status and a CORS console error, restart ng serve with the proxy flag. Never the cause in deployed environments.

Silent failure

200 but wrong screen data

API returned 200 but content is wrong or missing. Check the Response tab carefully. Compare against the TypeScript interface. A .NET schema change not mirrored in Angular interfaces is the usual cause.

Cascade

Multiple endpoints failing after one

Find the first red Network entry — that is the root cause. All subsequent failures are consequences of the first. Never investigate the second failure before fixing the first.

Race

Intermittent data loading

If data loads sometimes but not others, check the debugResponse trail. If a dependent call appears before its prerequisite, the Promise chain needs restructuring — chain dependent calls inside .then().

Lazy load

Feature module fails to load

ChunkLoadError with 404 — bundle not on server. Check build artefacts and deployment pipeline. Not a code bug. Check Network tab filtered by .js for the missing chunk filename.

Expert Scenarios

Expert Scenario Challenges

Four complex, multi-step situations requiring knowledge from all three levels.

Expert Scenario 1 — PR Review
A PR adds a new XuClaimsService method that sends a claimReferences array using xuWebApiManager.get(). The logic is correct. Should you approve it?
✅ Correct! Any array parameter must use xuWebApiManager.post(). This is exactly why changeHandler uses POST — its claimReferences array must be in the request body, not the query string. Reject the PR.
Expert Scenario 2 — Production Incident
The close claim button shows no error but the claim does not close. Network tab shows api/claims/invokeAction returning 400 with actionName=CloseClaim. errorObject contains: outstanding reserve must be zero before closing. Where is the bug?
✅ Correct! The API is working correctly — it enforced the business rule. The real bug is the component not handling the error. xuCloseClaimDialog's .catch() must read retVal.errorObject and show the message. Fix the component error handling.
Expert Scenario 3 — Lazy Load Failure
A user gets a blank LMM screen. Console shows ChunkLoadError: Loading chunk lmm-lmm-module failed. Network tab shows 404 for lmm-lmm-module.js. What is the root cause?
✅ Correct! A ChunkLoadError with 404 means the server does not have the bundle file. The Angular build should produce lmm-lmm-module.js. Check build artefacts first, then the deployment pipeline. Not a code bug.
Expert Scenario 4 — Race Condition
xuClaimOverallTotal sometimes shows wrong totals. The Console debugResponse trail shows getClaimOverallTotals completing before getClaimsPreviewData sometimes. What is the correct fix?
✅ Correct! Chain dependent calls inside .then(): getClaimsPreviewData(ref).then(preview => { this.preview = preview; return getClaimOverallTotals(ref); }).then(totals => { this.totals = totals; }). Never use setTimeout() for async sequencing.
