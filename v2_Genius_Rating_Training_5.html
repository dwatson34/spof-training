Genius Rating

How Genius automatically calculates premiums using rating tables, factors and routines — and how to set them up, maintain them and diagnose problems.

The Genius Rating subsystem automates premium calculations for high-volume lines like Motor and Household. Instead of manually entering premiums, underwriters see rate calculations appear automatically based on the risk details they enter. This module covers how that works — from the tables that store the rates, to the routines that perform the calculations, to what the underwriter sees on screen.

Rating Tables — The Building Blocks

Rating Tables hold the rate data. A table takes one or two input factors (e.g. vehicle group, driver age) and returns an output (a premium, rate or percentage). Tables are always two-dimensional — but multi-dimensional requirements can be solved by chaining tables together.

Single Value Tables

A single value table does one lookup and returns a result directly. One or two factors are used as the key. Examples: Area code → District code; Vehicle group + District → Premium amount; Driver age range + Coverage type → Discount percentage. The result can be a code, an amount or a percentage.

Key table options — click to explore

Use Option 7 before modifying or deleting any table. It shows every product and routine that references this table. Changing a table used by 12 products will affect premiums on all of them immediately. Work with Rating Tables → enter 7 against the table
Create a new table version with an effective date before making any changes. Prepare next year's rates without affecting current policies. The system activates the new version automatically on the effective date. Always work on the new version, never edit the live one directly.
Option 10 (Load) runs the API program to populate the table with all valid values — used when first creating a table. Option 12 (Entries) lets you view and edit individual table entries manually — used for ongoing maintenance and checking specific values.
Apply a percentage change or flat amount adjustment to all entries in a table at once. Essential for annual rate reviews — instead of editing hundreds of entries individually, Option 11 adjusts the whole table in one step. Always create a version first (Option 9), then adjust on the new version.
Tables are always two-dimensional (max two keys). For three or more rating dimensions, chain tables together. Example: first table derives an intermediate code from Vehicle Group + Cover Type; a second table uses that intermediate code + District to derive the final premium. Chaining solves the multi-dimensional requirement within the two-key constraint.

Scenario challenge — try it yourself

Scenario Challenge — Banded Table Calculation
A banded table has three bands: £0–1,000 at 2%, £1,001–5,000 at 1%, £5,001–10,000 at 0.5%. The policy liability is £7,000. What is the correct total premium?
✅ Correct! Banded tables apply each band rate only to the portion of the value within that band: (£1,000×2%)=£20 + (£4,000×1%)=£40 + (£2,000×0.5%)=£10 = £70 total.

Rating Factors, Messages & APIs

Click through the tabbed sections — Factors, Messages and APIs — then test yourself with the scenario challenge.

For a policy field to be used as a key in a rating table, it must first be registered as a Rating Factor. Factors link policy fields to the API programs that validate, retrieve and load their values. Rating Messages can be attached to any table entry and control what the underwriter sees — from information to a complete block on processing.

What is a Rating Factor?

A Rating Factor is a policy field formally registered for use in rating. Until it is defined as a factor, it cannot be used as a key in any table or routine.

Three API program links: (1) Validation/Selection API — checks and presents valid values to the user. (2) Retrieval API — fetches the actual field value from the policy during a live rating calculation. (3) Load API — populates rating tables with all valid values of this factor when the table is loaded.
Access via: Housekeeping → Rating Housekeeping Menu → Option 3 (Work with Rating Factors). Option 7 (Usage) shows which tables reference a particular factor — essential before renaming or deleting a factor.
Typical Motor rating factors include: Vehicle Group, District Code, Driver Age, Coverage Type, Engine Capacity, Years No Claims Discount. Each must be defined as a factor before any Motor rating table can use it as a key.

The four types of Rating Message

Any table entry can be flagged to trigger a message when that combination of factors is encountered. Messages are user-definable. Click each type to understand what it does.

Informational

Information Only

Displays a message to the underwriter during policy input. Processing continues normally — no impact on saving or premium calculation. Example: "Young driver discount applied"

Warning

Warning — can continue

Warns the user but allows processing to continue. The policy can still be saved. Example: "Driver under 25 — check your underwriting authority before proceeding."

Error

Error — blocks saving

Prevents the policy being saved until the condition is resolved. A premium IS calculated but the policy cannot be committed. Example: "No drivers under 30 allowed for Group 12 vehicles."

Terminal Error

Terminal Error — stops rating

Stops the entire rating calculation. No premium is produced. The policy cannot proceed at all. Example: "Risk unacceptable — refer to senior underwriter."

Key distinction: An Error still calculates a premium but blocks saving. A Terminal Error stops rating entirely — no premium is shown at all.

Rating APIs — two categories

Programs that fetch a specific factor value from the policy during a live rating calculation. Example: a Retrieval API for the Vehicle Group factor reads the vehicle group code from the current policy record and makes it available to the rating engine to use as a table key.
Programs used during table setup. The Select/Validate API checks that a factor value entered into a table key is valid. The Load API populates the table with all valid values of the factor in one step — used with Option 10 (Load) on the Work with Rating Tables screen.
Access via: Rating Housekeeping Menu → Option 4 (Work with Rating APIs). Option 7 (Usage) shows which factors use a particular API — important before changing or replacing an API program.

The Scripting Exception

⚠️
Important exception

Where IBM i scripting is used for policy input, standard rating routines cannot be used. A separate scripting API must be created for each rating factor involved.

This is a common source of confusion. If rating is not working on a scripted policy, this is the most likely reason — not a configuration error in the rating tables or routines.

Where to find out more: Refer to the System Administrator's Guide, section on Script Housekeeping, for guidance on creating scripting APIs for rating factors.

Scenario challenge

Scenario Challenge
An underwriter inputs a Motor policy. A message appears and they cannot save the record — but a premium IS shown on screen. What type of message has fired?
✅ Correct! An Error message blocks saving but the premium IS still calculated and shown. A Terminal Error would mean no premium at all. The key clue is "a premium IS shown" — that rules out Terminal Error.

Rating Routines — Chaining the Steps

Click ▶ Run to watch a routine execute step by step. Then explore the rules and test yourself with a scenario.

A Rating Routine is a defined sequence of calculation steps within a Product Version. Each step looks up a table, applies a calculation, and stores a result for use by subsequent steps. The routine attaches to a product at a specific level and runs automatically during policy input once all required fields are entered.

Watch a Motor rating routine run

Click to step through the routine
1

Step 1 — Look up base premium

Input: Vehicle Group (Row Key). Table: BASE_RATE. Result stored in factor CVGPRM as the starting premium for this coverage.

2

Step 2 — Apply district loading

Input: District Code (Row Key) + CVGPRM from Step 1 (Column Key). Table: DIST_LOAD. Adjusts the base premium for the vehicle's registration district.

3

Step 3 — Apply driver age factor

Input: Driver Age Range (Row Key) + Coverage Type (Column Key). Table: AGE_FACTOR. Applies discount for experienced drivers or loading for young drivers.

4

Step 4 — Risk acceptability check

Input: Driver Age + Vehicle Group. Table: RISK_CHECK. If the combination is unacceptable, a Terminal Error fires — rating stops at this step.

✓

Complete — store at Coverage level

The calculated premium is stored at Coverage level in the policy. The underwriter sees the result in the Rating Summary window.

The rules governing routines — click to explore

Steps must always be defined and processed bottom-up: Item → Coverage → Section Detail → Section → Master. Lower-level calculations feed their results into higher-level ones. You cannot skip levels or process top-down. This mirrors how the policy hierarchy works — the lowest-level detail must be known before the higher levels can be calculated.
A routine can be attached to a product many times, but every attachment must be at the same level — all at Item, all at Coverage, all at Section Detail, etc. Mixing levels within one routine is not allowed. If you need calculations at both Coverage and Section level, you need two separate routines.
Both Rating Tables and Rating Routines support versions with effective dates. Use Option 3 (Copy) on the Work with Routines screen to copy an existing routine as a starting point for changes. Set an effective date so the new version activates automatically. Current policies continue using the old version until their next renewal.
Use the Testing a Rating Routine facility (accessible from the Work with Routines screen) to run test calculations with sample factor values. Verify the output matches expected premiums before attaching the routine to any product. This is the only safe way to confirm a new or modified routine is correct.

Scenario challenge

Scenario Challenge — The Single-Level Rule
A developer wants to attach a Rating Routine to a Motor product: once at Coverage level for Comprehensive cover, and once at Section level for the overall Section premium. The same routine is to be used for both. Is this allowed?
✅ Correct! The single-level rule means a routine can be attached multiple times but always at the same level. Coverage and Section are different levels — two separate routines are needed. The routine can attach multiple times at Coverage, or multiple times at Section, but not one of each.

Rating in Underwriting — What the User Sees

Click the tabs to explore the Summary window, the Detail breakdown, and how overrides are stored. The mock screens show exactly what appears.

When an underwriter enters a policy on a rated product, rating windows appear automatically once all required fields are entered — no manual trigger needed. The system runs the Rating Routine and displays the results. Understanding these windows helps you support underwriters who are confused about why a particular premium was calculated.

The Rating Summary Window

Appears automatically after all rating fields are entered on the policy input screen. Shows high-level calculations and the resulting premium.

Rating Summary — Motor PolicyGenius UW
Policy: XUK0099001MU01A Coverage: COMP Base Premium: 350.00 District Loading (+): 35.00 Young Driver Loading: 52.50 -------- Total Premium: 437.50 BUR0010 Young driver discount waived 15 W F6=Detail F3=Accept F12=Back
Severity column: W=Warning, E=Error. A red message with E blocking the Accept function means an Error message has fired.

What the Summary shows

Each calculation step that contributed to the final premium is shown separately — base rate, loadings, discounts — so the underwriter can see exactly how the total was reached.
Informational, Warning and Error messages all appear in the Summary. If a Terminal Error fired, the underwriter would not reach this screen — they would see the error before any summary is displayed.
If the underwriter does not understand why the premium is what it is, pressing F6 switches to the Rating Detail view which shows every individual table lookup and step calculation. Essential for diagnosing unexpected premiums.

Reading the Detail screen

Each row shows one step: the table used, the exact factor values that were used as keys, and the result returned. If a step returned an unexpected value, you can see exactly which table was involved and which factor values were passed in — pointing you to the right table to investigate.
Available from within Underwriting Maintenance, this screen shows all individual factor values and table lookups for any existing policy. You do not need to re-enter the policy to see the rating calculation history — useful for investigating premium queries on already-committed policies.

How overrides work

An underwriter can override the system-calculated premium (the "book rate"). The override replaces what is displayed — but the original book rate is never lost.

Rating Summary — OverrideGenius UW
Total Premium (Book Rate): 437.50 Override Premium: 400.00 Override entered — both rates stored at Coverage F6=Accept Override F3=Cancel
Both rates stored: Book rate £437.50 AND override £400.00 are stored at Coverage level. Neither is lost.

What the override records

Both the original book rate AND the override amount are stored at Coverage level within the policy structure. The override is flagged so the system knows it differs from the book rate. Neither rate is overwritten or lost.
Because both rates are always stored, the system can report or enquire on the difference between book and quoted rates for any policy or group of policies. This allows underwriting management to monitor how frequently and by how much underwriters are deviating from the book rate — a key risk management tool.

Where rating results are stored

Always at Coverage level — Rating calculation amounts (both book rate and any override) are stored at Coverage level within the policy structure. This is the lowest level of detail, even if the rating attachment points to a higher level (Section, Master).
Coverage is the most granular level at which policy amounts are held. Storing rating results here provides the maximum detail for reporting and auditing. A Motor policy with four coverages (COMP, F&T, TPFT, TPO) stores a separate rating result at each coverage — giving a complete breakdown of how the total premium was built up.
Enquiries and reports on rating results always look at Coverage-level data. The Genius Enquiry module can show the rating breakdown for any policy. Differences between book and quoted rates can be extracted and analysed across any portfolio of policies.

Maintenance & Administration

Click ▶ Run to watch the safe annual rate review process. Then open the quick-reference accordions for step-by-step guides.

Rating tables need ongoing maintenance as rates change year on year. Option 11 (Adjust) provides an efficient mechanism for applying bulk rate changes — but always create a version first and test thoroughly before activating. This slide covers the safe process and provides quick-reference steps for common tasks.

The safe annual rate review process — click ▶ Run

Click to step through the rate review process
1

Option 7 (Usage) — know the impact

Before touching any table, check Option 7 to see every product and routine that references it. Know what will be affected before making any change.

2

Option 9 (Versions) — create a new version

Create a new table version with the effective date of the rate change. Work on this version only — never edit the live version directly.

3

Option 11 (Adjust) — apply the change

Enter the percentage change or flat amount on the new version. All table entries are updated in one step. No need to edit entries individually.

4

Test against a known scenario

Use Testing a Rating Routine with a policy where you know the expected premium. Verify the new version produces the correct result.

5

Activate on the effective date

The new version activates automatically. Current policies use the old version until renewal — no disruption to in-force business.

Quick reference — click to open

  1. Housekeeping → Rating Housekeeping Menu → Option 1 (Work with Rating Tables)
  2. F6 to add; enter Table ID, description, type (S=Single or B=Banded)
  3. Define Row Key factor, Column Key factor (if 2D), and Result Field
  4. Option 10 (Load) to populate the table with valid entries via the Load API
  5. Option 5 (Display) to verify entries are correct
  6. Option 7 (Usage) to confirm nothing unexpected is already linked to this ID
  1. Product Maintenance → Rating Attachment → Work with Routines
  2. Always use Option 3 (Copy) from an existing routine rather than starting from scratch
  3. Add steps in bottom-up sequence: Item first, then Coverage, then Section Detail, Section, Master
  4. Each step: specify table, input factors (row/column keys), result factor, and any calculation to apply
  5. Test using the Testing a Rating Routine facility with a sample scenario
  6. Attach to the product at the appropriate level
Copying an existing routine or table preserves the correct factor definitions, level attachments and step sequences from a working example. Building from scratch risks missing a configuration detail — often one that only becomes apparent when the routine fails during live testing. The Copy option is always faster and safer.
  1. Check whether any table versions have recently activated (Option 9 on the tables used by the routine)
  2. Use Option 7 (Usage) on the affected tables to confirm no unexpected routine is referencing them
  3. Check the Routine version — has a new version activated earlier than expected?
  4. Run Testing a Rating Routine with the affected scenario to see exactly which step produces the wrong result
  5. Check whether an underwriter has overridden the rate — this is stored separately and not a system error
🚨
Risk

Rating configuration changes on live products can immediately affect all new and renewed policies. Always test on a non-production environment first and verify with a known policy scenario before activating any change.
