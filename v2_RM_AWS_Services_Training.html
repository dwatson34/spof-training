Xuber on AWS

How the Xuber application is deployed and what the RM team is responsible for

Xuber runs on AWS in the EU-West-2 London region. The RM team is responsible for operational support - not building infrastructure, but keeping it running, monitoring it, and making controlled changes.

Infrastructure tiers

Route 53 and CloudFront - DNS and CDN
Application Load Balancer - ALB
EC2 - Web and App tier - Angular and .NET
EC2 - iSeries integration tier
RDS SQL Server and AS400 DB2
S3 - documents, backups and logs

RM team responsibilities

Daily monitoring

CloudWatch dashboards

Review CPU, memory and disk alerts. Check S3 backup jobs completed successfully each morning.

Incident response

Service restoration

Restart failed EC2 instances. Investigate hung processes. Check security group changes after connectivity incidents.

Controlled changes

Planned modifications

Resize instances, update security group rules, create S3 buckets. Always peer-reviewed and change-approved.

All actions are logged: AWS CloudTrail records every console action against your named IAM user. Every change is traceable.

Amazon S3 - Object Storage

Buckets, objects, versioning and the Xuber storage conventions

S3 stores files as objects in buckets. Xuber uses S3 for document storage, database backups, application logs and static assets. Understanding S3 is essential for backup and restore operations.

Xuber S3 bucket naming

Bucket naming standardConvention
xuber-{env}-{purpose}-{region}

xuber-prod-documents-eu-west-2
xuber-prod-db-backups-eu-west-2
xuber-prod-app-logs-eu-west-2
xuber-uat-documents-eu-west-2
Versioning

Always enabled on prod

Deleted or overwritten files can be recovered. Check versioning is enabled before any prod bucket modification.

Block Public Access

Always ON

All Xuber buckets block public access at account level. Never disable this. Access is via IAM roles only.

Common S3 tasks

Browse filesS3 Console, find bucket, use the search bar or navigate the folder structure. Prefix equals folder path.
Download a fileClick object then Download. For bulk: select objects, Actions, Download. Or AWS CLI: aws s3 cp s3://bucket/key ./local
Restore deleted fileEnable Show versions, find the version before deletion, download or remove the delete marker to restore.
Check lifecycle rulesBucket, Management tab, Lifecycle rules. Shows retention and transition policies including Glacier tiering.
Never delete from prod S3 without change approval. Even with versioning, bulk deletions are disruptive and require an approved change request.

Concept 3

Amazon EC2 - Virtual Servers

Starting, stopping, connecting to and monitoring Xuber EC2 instances

EC2 instances are the virtual servers running Xuber. The RM team must know how to safely restart them, check their health, connect for troubleshooting, and monitor resource usage.

xuber-app-prod

Application servers

Windows Server 2019, m5.2xlarge. Runs the Xuber application tier. 2 instances behind ALB for high availability.

xuber-db-prod

Database server

Windows Server 2019, r5.4xlarge. SQL Server 2019. Single instance - database backups are critical.

xuber-iseries

iSeries gateway

Linux c5.xlarge. Hosts the iSeries connectivity layer for AS400 communication.

xuber-bastion

Bastion host

Amazon Linux t3.micro. The jump server - all RDP and SSH to Xuber instances goes through the bastion.

⚠️
Restart order matters

Always restart in this order: iSeries gateway first, then application servers, then bastion. Allow 2 minutes between each restart for services to initialise. Restarting app before iSeries causes connection errors.

To connect to an instance: Use EC2 Session Manager - no SSH keys or open ports required. All sessions are logged to CloudTrail. This is the required method for Xuber.

Concept 4

Security Groups

Virtual firewalls controlling traffic to Xuber EC2 instances

A Security Group is a virtual firewall attached to an EC2 instance. It controls inbound and outbound traffic by port, protocol and source. Misconfigured security groups are the most common cause of Xuber connectivity incidents.

Xuber security group structure

sg-xuber-alb

Load Balancer

Inbound: 443 from internet. Outbound: all to sg-xuber-app.

sg-xuber-app

Application tier

Inbound: 443 from sg-xuber-alb only. Outbound: 1433 to sg-xuber-db.

sg-xuber-db

Database tier

Inbound: 1433 from sg-xuber-app only. Most restrictive - never add public access.

sg-xuber-bastion

Bastion host

Inbound: port 22 from DXC office IPs only. Outbound: RDP to app and database servers.

1

Identify what is needed

What port? What protocol? What source? Never use 0.0.0.0/0 as source for anything other than public web traffic.

2

Get change approval

All production security group changes require an approved change request including justification and rollback plan.

3

Add the rule

EC2, Security Groups, find the group, Inbound rules, Edit, Add rule. Always add a description explaining why the rule exists.

4

Test and document

Verify connectivity works. Update the Confluence runbook with the new rule and justification.

Never open port 22 or 3389 to 0.0.0.0/0. This exposes instances to internet brute-force attacks. Use Session Manager. Any such rule will be flagged by AWS Config immediately.

Concept 5

CloudWatch Monitoring

Where to look when something breaks in Xuber AWS infrastructure

CloudWatch collects metrics, logs and events from every Xuber AWS resource. It is the first stop when investigating any infrastructure incident.

Xuber-Prod-Overview dashboard

Production health

CPU, memory and response time across all production instances. Check this first during any incident.

Xuber-DB-Health dashboard

Database metrics

RDS CPU, connections, read and write IOPS, free storage space. Critical for slow query investigations.

Xuber-ALB-Metrics

Load balancer

Request count, 5xx error rate, target response time, healthy host count. First sign of application errors often shows here.

Log Insights

Application logs

CloudWatch, Log Insights, select /xuber/application. Filter by ERROR and sort descending by timestamp.

!

Alarm fires - check the metric

Open the alarm, view the graph. What threshold was crossed? When did it start? Is it recovering?

2

Check associated logs

CloudWatch, Log Groups, find the application or OS log group for the affected instance, filter by the alarm time window.

3

Correlate and act

High CPU? Check request count spike or memory leak. Fix the root cause. Document the incident with timestamps in the Xuber ops log.
