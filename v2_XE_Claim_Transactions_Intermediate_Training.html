The Base Class

Click each tab to explore what xuClaimsTransactionComponentBase provides to every transaction component.

xuClaimsTransactionComponentBase (352KB of TypeScript) is the heart of the claims transaction framework. It provides hundreds of methods that all transaction components inherit. Every component that creates, amends, deletes or views a claim builds on this foundation.

The base class provides:
  • All command handlers (amend, delete, add name involvement, add event etc.)
  • Screen menu item builders (buildScreenMenuItems(), buildScreenCommands())
  • R&P financial entry methods
  • Document handling commands
  • Coverage verification logic
  • Header status management
  • Custom rule management
  • Error display (errorMessageDisplay())
  • Tab close handling (onTabCloseClicked())
  • Transaction cancel (cancelTransaction())
  • Transaction complete (completeTransaction())
What each child class adds:
The 7 abstract method implementations only. Each child class is typically 80–120 lines, consisting almost entirely of the 7 required methods plus a constructor. The base class does everything else.
The base class accumulates every claim transaction behaviour that is shared across modes. Over years of development, new features (document production, coverage verification, layer claims, writebacks, R&P commands) have been added to the base class so they are available to all transaction types without duplicating code in each child component.

How the base class calls abstract methods

The base class calls these methods at specific points in the lifecycle. startNewTransaction() is called by the framework startup sequence. getHeaderTitle() is called when rendering the page header. saveButtonHandler() is wired to the Save button in the shared template. showTransactionCompleteDialog() is called by completeTransaction() when the API confirms success.

TypeScript enforcement: If you write a new transaction component and miss even one abstract method, the TypeScript compiler will refuse to compile. abstract is a build-time contract, not a runtime check.

The XuDeferred Pattern

Click ▶ to step through why every startNewTransaction() uses XuDeferred instead of returning a plain Promise.

XuDeferred is Xuber’s own Promise wrapper, imported from common/shared/services/XuDeferred. It is used in every startNewTransaction() method. Understanding it is essential for reading any transaction component.

The XuDeferred pattern — click ▶ to step through

Click to step through
1

Create the XuDeferred object

let transactionIdDefer = new XuDeferred<any>();
This creates a deferred Promise — a Promise whose resolve and reject functions are accessible externally, not just inside a constructor callback.

2

Call the API service method

startTransactionPromise = this.xuClaimsTransactionService.startAmendClaimTransaction(this.claimStage, this.claimReference);
This calls the API and returns a Promise from XuWebApiManager.

3

On success: resolve with transactionId

startTransactionPromise.then(data => { transactionIdDefer.resolve(data.transactionId); });
When the API responds successfully, the deferred is resolved with just the transactionId. The full API response is unwrapped here.

4

On error: display message and reject

startTransactionPromise.catch(error => { this.errorMessageDisplay(error); transactionIdDefer.reject(); });
On failure, the base class errorMessageDisplay() shows the error to the user and the deferred is rejected so the framework knows startup failed.

5

Return the deferred’s promise

return transactionIdDefer.promise;
The framework receives this Promise. When it resolves with the transactionId, the framework stores it and the screen loads. When it rejects, the framework cancels the startup sequence.

Complete real example — XuDeleteClaimTransactionComponentTypeScript
startNewTransaction() {
  let transactionIdDefer =
    new XuDeferred<any>();
  let startTransactionPromise:
    Promise<any>;

  startTransactionPromise =
    this.xuClaimsTransactionService
      .startDeleteClaimTransaction(
        this.claimReference,
        this.claimStage,
        this.transactionId
      );

  startTransactionPromise.then(
    data => {
      transactionIdDefer.resolve(
        data.transactionId
      );
    },
    error => {
      this.errorMessageDisplay(error);
      transactionIdDefer.reject();
    }
  );
  return transactionIdDefer.promise;
}

Why XuDeferred instead of returning the API Promise directly?

The API returns the full response object. The framework needs only data.transactionId. XuDeferred allows the component to unwrap and reshape the response — resolving with just the value the framework needs, not the raw API response.
By catching the error here and calling errorMessageDisplay(error), the component ensures the user sees a meaningful error message. Then transactionIdDefer.reject() signals failure to the framework. Returning the raw API Promise would mean error handling is left entirely to the framework caller.
XuDeleteClaimTransactionComponent and XuCloseClaimTransactionComponent both have a private transactionStarted: boolean = false guard. They check this in initiateWithTransactionId() before calling the API a second time. This prevents the transaction from being started twice if the component initialises multiple times.

Navigation & Routing

Click each tab to understand the real navigation patterns used in claim transaction components.

Claim transactions navigate between nodes (screens within a transaction) using Angular’s Router with a specific URL structure. Understanding this structure is essential when debugging navigation failures or adding new transaction screens.

navigateToNode — real source (all components)TypeScript
navigateToNode(
  nodeName: string,
  componentId: string,
  customNavigationStrategy: string,
  navigationData: string,
  transactionId: any
): Promise<boolean> {

  var routerURL =
    this.router.createUrlTree([
      '../../../../../',
      nodeName,
      componentId,
      customNavigationStrategy,
      navigationData,
      transactionId
    ], {
      relativeTo: this.route
    });

  return this.router
    .navigateByUrl(routerURL);
}

How this navigation works

createUrlTree builds a relative URL starting 5 levels up (../../../../../) from the current route. This is the same pattern across all 7 transaction components — a Xuber convention. The navigationData parameter carries an encoded object with context for the target node. XuObjectEncoderDecoder encodes and decodes this string.

The ../../../../../ path is fixed at 5 levels. This reflects the depth of the transaction route in the Angular router tree. If you see navigation landing on the wrong screen, the URL structure is likely correct — the issue is usually in the nodeName or navigationData values.
XuClaimTransactionUrlBuilder — typed URL constructionTypeScript
// From XuAmendClaimTransactionComponent:
startAmendTransaction(
  claimReference: string
) {
  let url =
    this.xuClaimTransactionUrlBuilder
      .buildAmendClaimTransactionUrl(
        this.navGraphName,
        claimReference,
        this.claimHeaderId,
        this.policyReference,
        this.redirectedComponentId
      );
  this.xuRouteManager
    .openUrlInOverrideTab(
      url, claimReference
    );
}

Why a dedicated URL builder?

XuClaimTransactionUrlBuilder centralises the construction of claim transaction URLs. Rather than each component building URL strings manually (which creates maintenance burden and typo risk), all URL building is delegated to typed methods. Methods like buildAmendClaimTransactionUrl() guarantee the correct URL structure and encode all required parameters.

// From XuAmendClaimTransactionComponent:
window.parent.xuEventPubSub

    Xuber.eventStore

Why window.parent?

The Xuber HTMLUI runs inside an iframe within the parent shell application. window.parent.overrideTab() calls a function on the parent frame to replace the current tab’s content. window.parent.xuEventPubSub.broadcast() sends events to the parent frame’s event bus. These cross-frame calls are a fundamental pattern in Xuber — the Angular app communicates with its shell container this way.

Concept 5

Display → Amend Transition

Click ▶ to step through the two code paths in onEditClaim() — open and closed claims behave differently.

When a user views a claim in display mode and clicks Edit, the transition to amend is not a simple navigation. It involves cancelling the display transaction, building a new URL, and opening amend in the same tab. But for closed claims, there is a different path.

The onEditClaim() logic — click ▶

Click to step through
1

User clicks the Edit button

The Edit button was added to screenMenuItems by createEditMenuItem() in ngOnInit. Its handler is onEditClaim(). The button is hidden if UpdateUIAccessMethod.ViaTaskOnly is set — meaning the user can only access the claim via the task list, not the direct edit button.

2

Check: is the claim Closed?

if (this.claimHeaderInternalStatus === ClaimStatus.Closed) — a closed claim takes a different path. Closed claims can still be amended in Xuber (to add notes etc.) but the transition works differently.

3A

Path A — Closed claim

this.xuClaimsTransactionService.startAmendClaimTransaction(this.claimStage, this.claimReference) — For a closed claim, the display component directly calls the service to start the amend transaction. There is no navigation — the current screen transitions in place.

3B

Path B — Open claim

Two things happen: this.cancelTransaction(true) cancels the display transaction (releases it silently), then window.parent.overrideTab(url, this.claimReference) replaces the current tab with the amend transaction URL. The display session ends and amend begins in the same tab.

4

Amend loads in the same tab

The parent frame receives overrideTab() and loads the amend URL. XuAmendClaimTransactionComponent mounts, its ngOnInit fires, startNewTransaction() is called, and the user is in edit mode on the same claim they were viewing.

onEditClaim — real source from XuDisplayClaimTransactionComponentTypeScript
onEditClaim() {
  if (this.claimHeaderInternalStatus ===
    ClaimStatus.Closed) {
    // Closed claim: start amend directly
    this.xuClaimsTransactionService
      .startAmendClaimTransaction(
        this.claimStage,
        this.claimReference
      );
  } else {
    // Open claim: cancel display, open amend in tab
    this.cancelTransaction(true);
    let url = this
      .xuClaimTransactionUrlBuilder
      .buildAmendClaimTransactionUrl(
        this.navGraphName,
        this.claimReference,
        null, this.policyReference, null
      );
    window.parent.overrideTab(
      url, this.claimReference
    );
  }
}

Scenario Challenges

Intermediate Scenario Challenges

Four real situations requiring Intermediate-level knowledge.

Scenario 1 — The Base Class
A new transaction component compiles fine but when the user opens it, the claimReference, policyReference and transactionId are all null. ngOnInit is confirmed as running via debugOnInit. What is missing?
✅ Correct! IntitateDefaultSection() is the base class method that reads route parameters and populates all the key properties. Every transaction ngOnInit must call it as the second step. Without it, all properties remain at their default null values.
Scenario 2 — XuDeferred
A developer rewrites startNewTransaction() to return the service call Promise directly: return this.xuClaimsTransactionService.startAmendClaimTransaction(...). The transaction opens fine. What is now missing?
✅ Correct! Two things are lost: (1) the response unwrapping — the framework expects just transactionId, not the full API response object; (2) error handling — errorMessageDisplay(error) is never called so failures silently reject with no user feedback.
Scenario 3 — Navigation
A user clicks Edit on a displayed claim and nothing happens. There is no Network tab activity and no Console errors. The claim status is not Closed. What is the most likely cause?
✅ For a non-closed claim, onEditClaim() calls cancelTransaction() then window.parent.overrideTab(). No Network activity means the code may not be executing at all. Check whether the Edit button is rendered (UpdateUIAccessMethod.ViaTaskOnly hides it). If the button IS visible, add a console.log at the start of onEditClaim() to confirm it fires.
Scenario 4 — The Known Typo
A developer wants to fix the IntitateDefaultSection typo (missing ‘i’) in the base class. They fix it in the base class declaration only and submit a PR. Should you approve it?
✅ Correct! IntitateDefaultSection() is called in every transaction component’s ngOnInit. Renaming the method in the base class while the call sites still use the old name breaks the TypeScript build immediately. This is the same class of problem as the UpdateManuaPremiumAmountChange typo — it requires a single coordinated change across all files.
