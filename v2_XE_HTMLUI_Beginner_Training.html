What is the Xuber HTMLUI?

Click each component in the system map to understand where the HTMLUI fits.

The Xuber HTMLUI is an Angular web application. It is the browser-based user interface that sits in front of the Xuber insurance platform. Users access it through a web browser — no installation required. Everything they see and click is HTML, TypeScript and CSS delivered by this application.

The Browser — what the user sees

The user opens a URL in Chrome or Edge. The Xuber HTMLUI Angular application loads into their browser. From this point, all navigation happens without page reloads — Angular handles routing internally. The browser is just a runtime environment; all the application logic is in the Angular code.

Key facts

Technology

Angular (TypeScript)

The HTMLUI is built with Angular — the same framework used by many enterprise applications. It uses TypeScript, which is JavaScript with type checking. If you see .ts files, those are TypeScript.

Location

Xuber.Web.AppUI

The Angular application lives in the Xuber.Web.AppUI project inside the XuberHTML repository on the DXC internal GitHub at github.dxc.com/XuberEnterprise/XuberHTML.

SPOF

Why it is Critical

Zero of the 28 XE team members currently have documented knowledge of how the API layer works. If the HTMLUI breaks and no one understands the code, it cannot be fixed. This is the definition of a Critical SPOF.

Routes

8 Feature Areas

The HTMLUI has 8 lazy-loaded feature areas: home, task, insurancedirectory, underwriting, claims, accounts, xlpro, lmm. Each loads only when the user navigates to it.

How a Request Works

Click ▶ to step through what happens when a user clicks on a claim in Xuber.

Every time data appears on screen in the Xuber HTMLUI, it arrived via an API call. Understanding the journey helps you know where to look when something goes wrong.

Step through a real request — clicking a claim

Click to step through
1

User clicks a claim in the list

The Angular component in feature/claims/ handles the click event and calls a method in XuClaimsService.

2

XuClaimsService builds the request

The service method creates a params object with the claimReference and calls this.xuWebApiManager.get('api/claims/getClaimsPreviewData', params).

3

XuWebApiManager prepares the URL

CorrectUrl() converts api/claims/getClaimsPreviewData to /XuberHTMLApi/api/claims/getClaimsPreviewData. Parameters are serialised into a query string using $.param().

4

Angular HttpClient sends the HTTP GET

The request goes to the .NET backend at /XuberHTMLApi/api/claims/getClaimsPreviewData?claimReference=XUK001&....

5

The .NET API processes the request

The XuberHTMLApi backend validates the request, fetches data from Genius, and returns a JSON response.

6

Data reaches the component

The Promise resolves. xuLoggerService.debugResponse(url) logs success. The component stores the response data and Angular updates the template — the claim preview panel appears.

The key insight: Every piece of data on screen followed this same 6-step journey. When something is blank or wrong, you need to find where in this chain the problem occurred.

Concept 4

Reading a Service File

Click each highlighted section of the real service code to understand what it does.

Every service file in Xuber follows the same pattern. Once you can read one, you can read them all. Let’s break down a real method from xuClaims.service.ts.

Click a section to understand it

The class declarationTypeScript
@Injectable()
export class XuClaimsService {
  constructor(
    protected xuWebApiManager:
      XuWebApiManager,
    private xuLoggerService:
      XuLoggerService
  ) {}
  // methods below...
}

What this means

@Injectable() tells Angular this class can be injected into other classes. The constructor declares two dependencies that Angular provides automatically: XuWebApiManager (for HTTP calls) and XuLoggerService (for debug logging). You never create this class with new — Angular manages it.

The endpoint constantTypeScript
private static
  getClaimsPreviewDataApiPath =
  'api/claims/getClaimsPreviewData';

// private = only used inside this class
// static = belongs to the class itself,
//          not each instance
// This is defined ONCE and reused
// by the method below

The naming convention

Every Xuber service method declares its API path as a private static constant immediately before the method that uses it. This is a Xuber code convention. You will see this pattern repeated for every method in every service file. The constant name always ends in ApiPath.

The method signatureTypeScript
getClaimsPreviewData(
  claimReference: string,
  claimDetailRef: string = null,
  eventId: number = null,
  isPreviewSourceTasklist = false
) {
  // body below
}

Parameters explained

claimReference: string — required, no default. claimDetailRef: string = null — optional, defaults to null if not provided. isPreviewSourceTasklist = false — a flag that changes what the API returns depending on where the call came from. If you see = null or = false, the parameter is optional.

Building the params objectTypeScript
var params = {
  claimReference: claimReference,
  claimDetailRef: claimDetailRef,
  eventId: eventId,
  isPreviewSourceTaskList:
    isPreviewSourceTasklist
};
// Note: param names in the object
// must match what the .NET API expects
// They may differ from the method
// parameter names (see isPreviewSource...)

The params object

All parameters are bundled into one params object. XuWebApiManager will serialise this into a query string. Notice that isPreviewSourceTasklist (method param) becomes isPreviewSourceTaskList (capital L) in the params object — this must match the .NET API parameter name exactly.

Making the callTypeScript
let url = XuClaimsService
  .getClaimsPreviewDataApiPath;

return this.xuWebApiManager
  .get(url, params)
  .then(response => {
    this.xuLoggerService
      .debugResponse(url);
    return response;
  });
// Returns a Promise, not Observable
// Use .then() not .subscribe()

The call and return

The service calls xuWebApiManager.get() with the URL and params. This returns a Promise. The .then() logs the URL on success and passes the response back to the caller. The whole method returns this Promise — the component that called the service waits for it to resolve.

Basic Debugging

The Network tab is your first tool for any HTMLUI problem. Click ▶ to step through the procedure.

When the Xuber HTMLUI does not behave as expected — blank panels, error messages, buttons that do nothing — the Network tab in Chrome DevTools shows you exactly what happened at the API level.

Basic debug procedure — click ▶ to step through

Click to step through
1

Open Chrome DevTools

Press F12. Click the Network tab. If there are existing entries, click the 🚫 Clear button to start fresh.

2

Filter by api/

In the filter box type api/. This hides all the CSS, JS and image requests and shows only Xuber API calls. Much easier to read.

3

Reproduce the issue

Now do the thing that is broken — click the claim, press the button, navigate to the screen. Watch the Network tab for new entries appearing.

4

Find the API call

Look at the URL column. You should see /XuberHTMLApi/api/claims/... or /XuberHTMLApi/api/underwriting/.... Red rows mean errors (4xx or 5xx). Green/white rows mean success.

5

Click the call and read the Status

Click the row. The Status code tells you what happened: 200 = success, 400 = bad request (wrong params), 401 = not logged in, 500 = server error.

6

Read the Response

Click the Response tab. This shows exactly what the API returned. If there is an error, the message here tells you why it failed. This is the most important information for diagnosing any HTMLUI issue.

Quick Check
A user says the claim preview panel is blank. You open the Network tab and see a red row: /XuberHTMLApi/api/claims/getClaimsPreviewData with Status 400. What does this tell you?
✅ Correct! A 400 means the request reached the server but was rejected as invalid. The most common cause in Xuber is a null or missing required parameter. Click the call and check the Response tab for the error message, then check the Query String Parameters to see what was actually sent.
