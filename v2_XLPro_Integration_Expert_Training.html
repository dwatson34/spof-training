Diagnostics

Troubleshooting Framework

Systematic diagnostic approach to resolving integration issues

When the integration fails, a systematic diagnostic approach saves time and identifies root causes. This framework guides troubleshooting from initial symptom through resolution.

Diagnostic Flow

Step 1: Confirm Symptom

Question: What is the user experiencing?
Check: Are messages stuck in Xuber queue? Is XLPro database not receiving updates? Are services crashing?
Review: Event Viewer logs, integration service status, database connection tests.

Step 2: Service Status

Check: Are integration services running on both servers?
Verify: Services started in correct order, no startup errors.
Look for: Service restart loops, permission errors, event log errors.

Step 3: Connectivity

Test: Can Xuber server reach XLPro database server?
Verify: Network connectivity, firewall rules, DNS resolution.
Use: `ping`, `telnet`, SQL Server client connection test.

Step 4: Authentication

Check: Service account credentials, database permissions.
Verify: Can service account connect to databases?
Test: Execute query with service account credentials.

Step 5: Message Flow

Check: Are messages being captured in Xuber?
Verify: Integration logs show event captures.
Monitor: Message queue depth, message rate.

Step 6: Processing

Check: Are messages being processed in XLPro?
Verify: USM Load service processing messages.
Monitor: Staging table growth and processing.

Common Issues & Quick Fixes

Messages Stuck in Staging Table

Symptom: xlpro_staging table grows continuously, messages not being processed.

Diagnosis: Check if USM Load service is running. Review xlpro_log table for processing errors. Check database permissions.

Fix: (1) Restart USM Load service. (2) Clear staging if messages are corrupt. (3) Verify service account permissions on database.

Service Fails to Start

Symptom: "DXC XLPro Integration" service appears in Services but shows Stopped or fails to start.

Diagnosis: Check Event Viewer for service startup errors. Common causes: invalid database connection string, service account lacks permissions, port conflicts.

Fix: (1) Verify connection string in config files. (2) Check service account permissions. (3) Review Event Viewer detailed error message and search support documentation.

Partial Data Synchronization

Symptom: Some policy fields sync to XLPro, others don't. Data incomplete in XLPro database.

Diagnosis: Check message transformation rules in messaging config. Verify XLPro database schema changes were applied completely. Review xlpro_log for transformation errors.

Fix: (1) Re-run database setup scripts on XLPro database. (2) Review and update message mapping configuration. (3) Test with a simple policy with minimal fields to isolate issue.

High Latency (Slow Synchronization)

Symptom: Data takes 5+ minutes to appear in XLPro after policy creation in Xuber.

Diagnosis: Check database query performance, network latency, CPU/memory on servers. Review xlpro_staging table size and indexing.

Fix: (1) Rebuild indexes on staging table. (2) Implement message batching. (3) Increase SQL Server memory allocation. (4) Profile and optimize slow queries.

Optimization

Performance Tuning

Optimization strategies for high-volume production environments

In high-volume environments, performance tuning prevents bottlenecks and ensures SLA compliance. Optimization focuses on database performance, queue management, and resource allocation.

Database Optimization

Index Strategy

Clustered Index: Keep xlpro_staging clustered on (message_id, created_date) for efficient sequential scans.
Non-Clustered: Add indexes on (status, created_date) for filtering processed vs pending messages.
Maintenance: Schedule index rebuilds during low-usage windows to maintain performance.

Table Partitioning

Strategy: Partition xlpro_staging by created_date (monthly partitions) to improve query performance and enable faster data archiving.
Benefit: Queries scan only relevant partitions, reducing I/O and improving speed.
Implementation: Requires Enterprise Edition of SQL Server.

Archive Strategy

Policy: Archive processed messages older than 90 days to a separate table or database.
Benefit: Keeps active staging table lean, improves query performance.
Procedure: Weekly batch job to move completed messages to archive table with index.

Query Optimization

Analysis: Use SQL Server Execution Plans to identify slow queries.
Optimization: Add computed columns for frequently filtered conditions, pre-aggregate counts in summary table.
Monitoring: Track query execution times and alert on degradation.

Message Processing Optimization

❌ Single Message Processing
Behavior: USM Load processes one message at a time. High overhead for each message.
Impact: High latency, CPU underutilized, slow throughput.
Use: Low-volume dev/test environments only.
✓ Batch Message Processing
Behavior: USM Load batches 100-500 messages and processes together. Lower overhead per message.
Impact: 3-5x throughput improvement, lower CPU, better resource utilization.
Use: Production environments with 100+ messages/minute.

Resource Allocation

SQL Server Memory

Recommendation: Allocate 60-75% of available server memory to SQL Server for production databases. Example: 16GB server → allocate 10-12GB to SQL Server. This enables larger buffer pool and better caching.

Connection Pool

Setting: Configure max pool size = (CPU cores × 4) + 4. Example: 8-core server → pool size of 36. Prevents connection starvation under load.

Message Queue

Configuration: Set queue depth limit to 10,000 messages. Prevents unbounded memory growth if processing slows. Enables early detection of bottlenecks before queue exhaustion.

Operations

Production Monitoring & Alerting

Setting up comprehensive monitoring for production support

Production support requires proactive monitoring to identify issues before they impact users. Comprehensive monitoring covers service health, message flow, database performance, and business metrics.

Monitoring Strategy

Service Health

Monitors: Service running status, process CPU/memory usage, thread count.
Alert Thresholds: Service stopped, CPU > 80%, memory > 85%.
Action: Immediate notification to on-call support, automatic restart policies.

Message Flow

Monitors: Messages received/processed per minute, queue depth, processing lag.
Alert Thresholds: Processing lag > 5 min, queue depth > 5,000, message rate drops > 50%.
Action: Alert support for investigation, automatic health check.

Database Performance

Monitors: Query execution time, disk I/O, lock waits, table growth.
Alert Thresholds: Query > 5s, disk utilization > 90%, staging table > 100K rows.
Action: Performance analysis, index maintenance, archiving decisions.

Monitoring Tools

Event Viewer

What: Windows application and system event logs. Where: Local monitoring on each server. Watch for: Service start/stop, permission errors, unhandled exceptions.

SQL Server Logs

What: SQL Server error log and agent logs. Where: SQL Server Management Studio → Management → SQL Server Logs. Watch for: Login failures, deadlocks, I/O errors.

Integration Logs

What: XLPro integration diagnostic logs. Where: C:\Program Files (x86)\DXC\Xuber XLPro Integration\logs\. Watch for: Message processing errors, database connection failures.

SQL Queries

What: Custom SQL queries for business metrics. Where: Query staging/log tables for sync status, message counts, error rates. Watch for: Declining message rate, increasing error counts.

SLA Definition

Message Processing SLA: 99% within 2 minutes

99% of policy events created in Xuber are synchronized to XLPro database within 2 minutes of creation. Monitored via xlpro_staging table lag metric.

Service Availability SLA: 99.5% uptime

Integration services remain available and processing messages for 99.5% of business hours. Excludes planned maintenance windows. Measured via service status monitoring.

Error Rate SLA: < 0.1%

Less than 0.1% of incoming messages result in processing errors. Monitored via xlpro_log error count metric. Requires root cause analysis and fix for any trending increase.

Best Practices

Operational Excellence

Proven practices for managing XLPro integration in production

Operational excellence comes from consistent application of best practices. These practices reduce incidents, speed resolution, and improve overall system reliability.

Change Management

Pre-Deployment Testing

Procedure: All configuration changes tested in UAT environment first. Test with production-like data volume (50-100k messages).
Validation: Message latency, error rate, resource utilization confirmed in test before applying to production.

Change Windows

Policy: Deploy changes during low-volume windows (weekend mornings, 11pm-6am).
Communication: Notify business stakeholders 48 hours before changes. Have rollback procedure documented and tested.

Rollback Procedure

Documented: Rollback steps for every change, including database schema reverts and service restarts.
Testing: Rollback procedure tested in UAT before applying change to production.

Audit & Documentation

Change Log: Every deployment documented with date, change details, approver, and rollback test results.
Configuration Baseline: Keep snapshot of working configuration files for each release.

Operational Procedures

Daily Health Check (5 minutes)
1. Check integration service status on both servers - should be "Started"
2. Query xlpro_staging table count - should match expected volume
3. Review integration logs for ERROR level entries - should be minimal
4. Check disk space on both servers - should be > 20% free
5. Document results in daily log
Weekly Maintenance (30 minutes)
1. Rebuild indexes on xlpro_staging and related tables
2. Update database statistics for optimizer accuracy
3. Archive processed messages older than 90 days
4. Review performance metrics (latency, throughput)
5. Update runbook with any new issues encountered
Monthly Review (1 hour)
1. Capacity review - message volume trends, peak loads
2. Performance analysis - latency, error rates, SLA compliance
3. Error analysis - review top error patterns from xlpro_log
4. Infrastructure review - disk, CPU, memory headroom
5. Planning - identify upgrades or optimizations needed

Incident Response

P1 Incident (Severe)

Condition: Integration down, no messages syncing, business operations impacted. Response Time: 15 minutes. Action: Page on-call support immediately, engage lead architect, begin RCA, enable verbose logging.

P2 Incident (Moderate)

Condition: Performance degraded (latency > 10 min), some messages delayed. Response Time: 1 hour. Action: Investigation, performance analysis, monitoring increase, potential database maintenance.

P3 Incident (Minor)

Condition: Occasional sync delays, warning-level errors. Response Time: 4 hours. Action: Log issue, investigate during next change window, may defer to planned maintenance.

Root Cause Analysis (RCA): For all P1 and P2 incidents, document RCA within 24 hours. Include: symptom, timeline, contributing factors, root cause, corrective action, and preventive measures. Share with team for learning.
