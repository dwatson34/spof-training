Testing Genius using SmartTest

SmartTest is the automated regression testing framework that validates Genius after every cumulative PTF. This module covers the architecture, how to run scripts, triage failures, and prepare for PTF releases.

SmartTest is an automated regression testing framework that validates Genius and Genius 2.0 environments after cumulative PTFs and code changes. It uses synthetic test data and scripted screen flows to confirm that core insurance processing behaviour has not been broken by a release. It runs only in DXC internal test environments and never touches customer data or production.

Architecture & Libraries

SmartTest is implemented as a set of IBM i libraries that separate data, programs, objects and journals. This separation protects the baseline test data and allows rollback to a known good state at any time. Understanding which library does what tells you where to look when something goes wrong.

XGGNDRT — SmartTest Data Library

Contains all the synthetic test data used by the SmartTest scripts. This is the baseline data that scripts read and update during execution. The rollback process restores this library to its clean baseline state. Never modify test data directly — always use the rollback to restore.

Save file naming convention

The suffix uses the first two digits of the PTF level number. PTF 5800 → suffix _58. PTF 6000 → suffix _60. PTF 6200 → suffix _62. Four save files are renamed at each PTF cycle: XGGNDRT, XGGNSRT, TM_LIB and TM_SAV.
Due to space constraints, save file backups older than the current and previous cumulative PTF should be deleted. Keeping two PTF levels of save files allows rollback to the previous release if needed.
SmartTest is deployed on GN02 (Core / Genius 1.x and 2.0) and GNXL (Genius XL). Always confirm which environment you are working on before running scripts — changes on the wrong machine can corrupt the baseline data.

Example — PTF 6000 save files

Library SMARTTEST — save files at PTF 6000IBM i
/* Current PTF = 6000 (suffix = _60) */

XGGNDRT_60  /* Data Library backup     */
XGGNSRT_60  /* Program Library backup  */
TM_LIB_60   /* Object Library backup   */
TM_SAV_60   /* Journal backup          */

/* Also keep previous PTF (5800): */
XGGNDRT_58  XGGNSRT_58  TM_LIB_58  TM_SAV_58

/* Delete anything older than _58  */

Running SmartTest Scripts

Click ▶ Run to watch each step appear in sequence. Follow this procedure every time without shortcuts.

Script execution follows a strict 8-step procedure. Every step matters — skipping the rollback is the most common cause of failures that aren't real failures, and running GT006000 and GT007000 separately is a known cause of data corruption. Follow the procedure exactly.

Click ▶ Run to step through the full execution procedure

Click to step through the procedure
1

Log in with your own IBM i profile

Always log in with your personal ID. Script execution itself runs under the shared GGNST4 profile — you enter this password when prompted at step 7.

2

Enter the ST command

Type ST and press Enter to reach the SmartTest menu.

3

Check background jobs — WRKSBSD QBACKGR

End all subsystem jobs with XGGNDRT in their name before proceeding. Active jobs here will cause data conflicts.

4

Navigate to scripts: 1 → 11 on Genius → option 19

This takes you to the script list where you can see all available scripts and their status.

5

Close and delete all Data Runs (option 12)

Option 9 to close any open runs, then option 4 to delete them. Status must show Closed for all before proceeding. Leftover runs from a previous session will corrupt your results.

6

Rollback (option 23) — ALWAYS required

Rollback resets test data to its baseline state. This step is mandatory before every script run — no exceptions. Skipping it is the most common cause of false failures.

7

Run the script (option 8)

Select option 8 against the script you want to run. Enter the GGNST4 password when prompted. The script executes and results are captured.

8

Review results

If no major issues: replace current version using Shift+F4 → Enter → Enter. Use F11 to compare original vs current, F10 to check errors line by line.

⚠️
GT006000 and GT007000 — special rule

These two scripts are related and must be run together in one go. Never perform a rollback between GT006000 and GT007000. Run them back-to-back as a single session.

Recommended script execution order

Claims cannot be tested until Underwriting succeeds — claims need valid policies to exist. Reinsurance needs both policies and claims. Journals need all prior processing to be complete. Never skip a group or run them out of sequence.
Core navigation and reference data scripts. Must pass before anything else. Validates basic Genius access and account setup. If these fail, stop and investigate the environment before running further scripts.
The core validation suite. Covers the full policy lifecycle — new business, endorsements, renewals and cancellations. This is the most important group. GT006000 and GT007000 are within this group — remember the special rule.
Claims (GT011000–GT013000) require successful Underwriting. Reinsurance (GT014000–GT017000) run when stable. Journals (GT018000+) are the final step — financial posting validation.

Failures & Triage

Cosmetic Failure

Cause: Screen title, spacing, column width or alignment has changed.
Action: Accept the difference if business logic is unaffected. Do not re-capture.
Re-capture? No — cosmetic changes alone never justify re-capture.

The re-capture decision — click to explore

  • Date/time differences — mask only
  • Screen title length or alignment change — accept
  • Data collision or leftover runs — rollback and re-run
  • Navigation failure before any business logic ran
  • Failure not reproducible after a clean rollback
A confirmed functional change has been introduced by the PTF and re-capture has been explicitly approved. This is the only valid reason. The change must be confirmed (not suspected), functional (not cosmetic or volatile), and approved (not self-authorised).
F11 — Compare Original vs Current screen side by side. Use this first to see what has changed.
F10 — Check errors line by line. Place your cursor on the small window and press F11 for a detail view of a specific difference.

Scenario challenges

Scenario 1 — Triage This Failure
A script fails. Investigation shows the comparison difference is that a date/time stamp on a screen has a different value than when the script was recorded. What is the correct action?
✅ Correct! Date/time mismatches are Volatile Data failures. The fix is masking — tell SmartTest to ignore that field in comparisons. Re-capture is never needed for date/time differences.
Scenario 2 — Triage This Failure
A script fails and the difference is that a core business calculation now produces a different result than the original. The PTF release notes confirm this calculation was NOT changed. What category is this and what should you do?
✅ Correct! An unexpected change to a business calculation that is not in the release notes is a Functional Regression — a potential defect. Log it and escalate to engineering immediately. Do not re-capture. This is exactly what SmartTest is designed to catch.

PTF Preparation

Click the tabs to work through the Before PTF steps, then the After PTF steps. Both must be completed in the correct order.

Applying a new cumulative PTF to the SmartTest environment requires preparation before the PTF is applied, and further steps after. Getting these wrong corrupts the baseline or loses the ability to roll back. Follow the procedure exactly.

Before the PTF is applied — click ▶ Run

Click to step through the Before PTF steps
1

Rename existing save files

In library SMARTTEST, rename XGGNDRT → XGGNDRT_58 (using the current PTF suffix). Repeat for XGGNSRT, TM_LIB, TM_SAV. This preserves the current baseline.

2

Create new save files

Create new save files named XGGNDRT, XGGNSRT, TM_LIB and TM_SAV (no suffix). Enter option 13 against each to update the description, e.g. "SmartTest Data Library at 6000".

3

Identify new Physical Files in the PTF

Go to the CRs and enter *FILE in the Text field. Enter option 8 against listed CRs. Note the CR and DDS name of any new Physical File. Verify creation date via DSPOBJHST.

4

Hand over to Richard

Richard now applies the PTF to the SmartTest libraries. The After PTF steps begin once his work is complete.

After the PTF is applied — click ▶ Run

Click to step through the After PTF steps
1

Confirm no active Data Runs

Check that no data runs are running and background jobs are not active. Check subsystem QBACKGR.

2

End Protection (End Journalling)

GENIUS Appl/Module: options 11, 19, 17 → Enter → Confirm. Verify Protected = No for all files in TM_SAV.

3

Perform Rollback

In SmartTest, perform the rollback (option 23) to reset to baseline state.

4

Refresh SmartTest Data Library

GENIUS Appl/Module: options 11, 19, 5, 8 → Enter → Confirm. Updates SmartTest to include any new Physical Files from the PTF.

5

Verify new files added

Option 5 (Work with Libraries) → 12 (Work with Objects) → enter the new Physical File name. Confirm it now exists in XGGNDRT.

6

Start Protection (Restart Journalling)

Options 11, 19, 15 → Enter → Confirm. Verify Protected = Yes for all files in TM_SAV.

7

Apply Forward and Backup

Options 11, 19, 23 → option 9 against Present to set new starting point. Then save all four libraries using SAVLIB jobs to the new save files.

Example SAVLIB jobCL
SBMJOB CMD(SAVLIB LIB(XGGNSRT) DEV(*SAVF)
             SAVF(SMARTTEST/XGGNSRT)) JOB(XGGNSRT)

Capturing Scripts & Masking

Explore when capturing is appropriate, how masking works, and the critical rules around Apply Forward.

Re-capturing scripts is an advanced and consequential task. Done without approval or for the wrong reason, it permanently overwrites the SmartTest baseline. This slide covers the correct use of capture and masking, the Apply Forward procedure, and known issues to watch out for.

Masking — the right fix for volatile data

Masking tells SmartTest to ignore specific fields or screen positions when comparing the current run against the recorded baseline. A masked field is excluded from the comparison — so even if its value changes on every run, it will not trigger a failure.
  • Dates and timestamps that change on every run
  • System-generated sequence numbers
  • Reference numbers or IDs created fresh each time
  • Any non-deterministic value the system generates automatically
If a failure can be resolved by masking the volatile field, there is no need to re-capture. Masking is reversible and low-risk. Re-capture permanently changes the baseline and requires approval. Always exhaust masking options before considering re-capture.
🚨
Apply Forward — use with extreme care

Apply Forward (option 9 against Present) permanently records the current state as the new SmartTest baseline. Only do this when you are certain all scripts run successfully and the changes are correct. This is not a routine step.

Known issue — Duplicate Policy
If a script attempts to create a policy that already exists (e.g. policy 010846 001), delete the duplicate policy first, then re-run from a clean rollback. This is a data state issue, not a script failure.
